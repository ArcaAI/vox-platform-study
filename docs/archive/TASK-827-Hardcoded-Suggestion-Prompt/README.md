## 1. The defect
`_SUGGESTION_SYSTEM_PROMPT` (`apps/harness/src/harness/temporal/interpreter/nodes/consultation_realtime.py:411`,
used at `:465`) is a Python constant. The node `consultation.suggestions` runs on it.

Identical in class to TASK-826, in the **same file**, and it violates the same rule:
*"an engine name, model id, endpoint, credential, threshold, **prompt**, taxonomy or label set is NOT
a literal in code"* (`.claude/rules/00-project-context.md` §Configuration Principles).

A tenant cannot see, change or version-pin how suggestions are generated.

## 2. TASK-826 is the template, and it is a short one
That lane established the whole path, so this is mostly repetition of a proven shape:
- resolve `config.promptTemplateId` through `_llm_policy.resolve_instruction` — unbound / unapproved /
  missing / empty each DEGRADE with a named code and never reach a model;
- resolve **before** the work begins, so a misconfigured node is visible on every run rather than only
  on runs that produce output;
- seed the platform default as a **SYSTEM-tenant** `PromptTemplate` (826 used
  `71000000-…-044` / version `72000000-…-033`) and assert `tenantId === SYSTEM_TENANT_ID`, and
  separately assert it is NOT the Global customer tenant;
- bind it on the node in both ArcaAI graphs and regenerate seeds **by script**.

**Expect no registry checksum move**: `consultation.suggestions` should already spread
`PROMPT_BINDING_PROPERTIES` like its sibling — verify rather than assume. The graph and compiled-config
checksums will move, as they must.

ancestor of `dev-2.2`, so the correction was a fast-forward, but a lane that had started editing
before checking would have created the files from scratch on a base three weeks stale.

**The TASK number did not need assigning.** The ticket asked for the usual "find the highest,

an artefact of the same stale base. This ticket already existed on `dev-2.2` as TASK-827, opened by

**Prediction 4 held exactly.** `consultation.suggestions` already spread `PROMPT_BINDING_PROPERTIES`

unchanged. Both graph checksums moved, as they must.

## 6a. The seeding constraint the ticket named, and why it is load-bearing

`DEFAULT_PROMPT_VERSIONS` derives each version id from the template's **array index**
(`V${i + 1}`), so the new row had to be appended at the END — index 44 → `V45`
(`72000000-…-045`). Inserting it anywhere earlier would silently re-point every later template's
version row at an id that already exists in deployed databases. The ticket flagged this; the seed
test now pins it directly (`the append-only tail held`) rather than trusting the comment that
states it, and asserts every version row still lines up with its own template index-for-index.

## 6b. A third prompt body, not a reuse of either neighbour

`LIVE_SUGGESTIONS_SYSTEM` (`…045`) is a distinct body from both `LIVE_GRAMMAR_SYSTEM` (`…043`) and
`NOTE_CORRECTIONS_SYSTEM` (`…044`), and the difference is what the pass is *for*. Both correction
bodies REVIEW existing words for error and are told to add nothing. This node's entire purpose is
to raise what is **absent** — an "omission" is by definition not in the text. An instruction built
around "correct only what is genuinely wrong, add nothing" is the opposite of what W2 needs.

So its safety bar could not be "add nothing"; it is the narrower "ground every item in the supplied
text, and never assert". The two failure modes it is written against are a suggestion stated as a
FINDING (a clinician reads these mid-consultation, so a confident false positive is the expensive
kind of wrong) and an invented detail dressed as something already established.

## 6c. The mutation that actually holds the line

Both mutations the ticket asked for were run, and the second is the one that matters:

Measured over `test_realtime_capability_nodes.py` + `test_realtime_delivery.py` (43 tests):

1. the deleted literal restored verbatim as a fallback → **6 RED**, including the source-level
   `test_the_module_holds_no_suggestion_prompt_literal`;
2. a fallback with **none of the literal's giveaway phrases** → **5 RED** on the behavioural tests
   while **the source-level grep PASSED**.

(2) reproduces TASK-826's finding on this node: a grep-only guard would have read green while a
paraphrased default crept back in. The behavioural tests, not the grep, hold the line.

One test in the new suite exists only because of (2)'s shape:
`test_resolution_precedes_the_policy_call_so_a_misconfigured_node_is_always_visible`. Resolving
after `_resolve_selection` would let an unbound node report `policy_fetch_unreachable` whenever the
policy plane was also down — a permanent configuration gap masked by a transient fault, on exactly
the runs an operator investigates.

### Two environment notes for the next lane in a fresh worktree
A fresh worktree needs `pnpm install`, `pnpm gen:prisma generate --all`, and a **full `pnpm build`**
before these suites mean anything. Skipping the build produces failures that look like real
regressions but are unbuilt workspace packages: `@arcaai/database` test failed on
`@arcaai/json-schema-subset` not being built, and `@arcaai/applications` build failed on
`@arcaai/exceptions` / `@arcaai/domains`. `gen:prisma` additionally needs `.env.dev` / `.env.test`,
which are gitignored and therefore absent from a new worktree — copy them from the main checkout.

Separately, running `api` / `applications` tests **concurrently with** a workspace build reports
large phantom failures (182 and 3 suites) as vitest reads half-written `dist/` files. Both were
clean on a re-run after the build settled. Let the build finish first.
