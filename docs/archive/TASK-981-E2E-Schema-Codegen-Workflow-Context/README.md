## Current State Evaluation (verified 2026-09-16 on `d79c0c25e`, dev DB reseeded 16:05 that day)

- **Hop chain (code-verified, then observed live):** `ConsultationController.open` → `ConsultationService.getOrCreate` → `resolveOpenContext` (two-pass: department by code via `DepartmentRepository.findByCode`, then `assertContextConformsToSchema` against the PINNED version; markers via `openBindingsFromDefinition`) → `resolveIdentityClinicianId` → `ContextUserIdentityService.resolveOrProvision` → `ConsultationFactory.CreateNewVisit` (`departmentId`, `doctorId`) + `withVisitTypeMarker` / `withExternalRefMarker` on `metadata` → `persistOpenContext` (one STRUCTURED item per validated kind with `kindKey`, one `CASE_NOTE` per `previous_case_notes.notes[]`) → `authoredContextOf` → `ConsultationWorkflowDispatchService.dispatchForConsultation` (`WorkflowAssignmentService.resolve(tenant, 'core', departmentId, visit-type tags)`) → `HarnessGatewayService.startWorkflowRun({ subject, payload: authoredContext })` → harness `start_workflow_run` → `interpreter_core_trigger` validates against the FROZEN `contextSchema.resolved` → run context `{ trigger, vars, nodes }` → `core.condition` on `trigger.context.visit_type` → `core.agent` prompts via `render_template` (`{{path|default("…")}}`).
- **Realtime lane:** `LiveDocumentationService.realtimeRunContext` (TASK-951 D-7) DOES read the client `vitals` / `previous_case_notes` items by `kindKey` and feeds `formatted_vitals` / `formatted_previous_visits` — but that context is consumed only by the live-lane department templates (v3), which reference neither variable. The WARM-START pre-summary — the one prompt whose template renders `{{context.safe_vitals}}` and `{{context.formatted_previous_visits}}` — runs through `LivePreSummaryAdapter` → `SummaryService.generatePreSummary` → `PromptAssemblyService`, whose `buildPreSummaryVariables({ currentDepartment, visitType, language })` call (`prompt-assembly.service.ts:862`) passes NO `vitals` / `previousVisits` source. The client's prior notes still reach that prompt, but only as the `CASE_NOTE` records in its `transcript` data section.
- **Frozen trigger schema** on every `arcaai-<dept>-consultation`: `contextSchema.resolved` = the v1 payload schema with `additionalProperties: false` at the KIND level; the STRUCTURED kinds' own `fields` declare no `additionalProperties`, so an added optional PROPERTY passes (proved: `chief_complaint`) but an added KIND does not (proved: `referral`).
- **Seeded ArcaAI content:** two schemas, 11 departments by code, 11 DEPARTMENT `WorkflowAssignment` rows + 1 TENANT default (GEN), 22 `arcaai-<dept>-summary-{new-visit,revisit}` agents, `case-notes-pre-summary`, `casenote-finalization`, `medical-ner`, `realtime-transcription` v2.
- **Seeded API-key gap:** the ArcaAI SDK key (`SDK_DAY_ONE_SCOPES`) lacks `agent:definition:read` / `workflow:definition:read`, so `vox-codegen --api-key … --agents --workflows` answers 403 with it; the tenant admin issued a key with those scopes (A3) and the generator then worked.

## Implementation Summary

### What the run proved

1. **Tenant admin → schema.** The tenant admin's own credential governs the schema: publish, classification, pin and discovery all moved without super-admin involvement, and the very next `open` was validated against the new version (the v2 property was accepted and persisted, and reached the harness trigger).
2. **Codegen → client.** Both generator modes work against the live gateway; the emitted types are exactly the tenant's vocabulary (enum of two visit types, required department code, role tags), and a typed client cannot build an off-schema payload. The published-catalogue types additionally expose the FROZEN trigger contract of each workflow — which is how a developer can see that a schema change has not reached a workflow (B2 vs B1 differ on `chief_complaint`).
3. **Open → mappings → provisioning → dispatch.** One request with no `departmentId` and no `clinicianUserId` produced a consultation in the right department, owned by a clinician provisioned from the staff id, with visit type and external ref recorded, its context persisted as typed items, and a department-selected workflow already running — in 0.8 s. The same staff id on a second open resolved to the same user.
4. **Durable run → context.** The Temporal start input and the `core.trigger` output are byte-for-byte the client's context; `core.condition` branched on the stated visit type; the interpreter completed finalizer → review → output once the gate was released through the SDK.
5. **Prompts.** Department and visit type reach every prompt through the template fragments ("for General Medicine … NEW or REFERRAL", "Breast & Endocrine Surgery … REVIEW (follow-up)"); the client's prior notes reach the department summary agent (`clinician_notes` section) and the warm-start pre-summary (as its input records).

### Defects found (owner decision needed — nothing changed here)

| # | Defect | Where | Evidence |
|---|---|---|---|
| **D1** | Client-supplied `vitals` never reach a prompt, and `previous_case_notes` never reach `formatted_previous_visits`. The pre-summary rendered `Recent Vitals: Not available (two most recent encounters)` and `Previous Visits:` empty while the run payload carried both. Root cause: `PromptAssemblyService` calls `buildPreSummaryVariables({ currentDepartment, visitType, language })` with no `vitals` / `previousVisits` source (`packages/applications/src/services/consultation/prompt/prompt-assembly.service.ts:862`); the TASK-951 D-7 wiring lives only in `LiveDocumentationService.realtimeRunContext`, whose consumers (the v3 department templates) reference neither variable. `handoffClinicalContext` (`live-documentation.service.ts:6644`) has the same gap. | applications | `C3-presummary-prompt.txt` (`Recent Vitals: Not available`), `C2-longest-gemma-prompt.txt` / `C3-live-lane-prompt.txt` (no `128/82` anywhere), `C2-temporal-start-input.json` (vitals present in the payload) |
| **D2** | Schema evolution is not interlocked with the published workflows. A tenant admin can publish + pin a version that adds a KIND; discovery and `open` accept it (201, run dispatched), and the FROZEN trigger of every consultation workflow then rejects the payload (`additionalProperties: false`), so the run FAILS at `core.trigger` while the consultation stays `OPEN` with `governingEngine` pointing at the failed run and no signal to the caller. Options for the owner: (a) refuse/warn at publish when a pinned-default change is not accepted by the frozen triggers bound to that schema, (b) let the trigger validate against the schema version the consultation was opened with, or (c) re-freeze bound workflows on pin. | applications + harness | `S3/S3-open-with-new-kind.txt`, `S3-temporal-node-results.json` |
| **D3** | The seeded ArcaAI SDK key cannot run the published-catalogue codegen (`agent:definition:read` / `workflow:definition:read` missing from `SDK_DAY_ONE_SCOPES`), so the documented `vox-codegen --api-key … --agents --workflows` fails 403 out of the box; ALaaS hit the same wall (memory 2026-09-11). Decide whether the day-one scope set should include the two read scopes. | database seed | `B2` first attempt in this session's log; `A3` shows the governed workaround |
