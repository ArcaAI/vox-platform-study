## Requirement Analysis

Owner request (verbatim intent): review every `.env*` file in the repo, remove what's unnecessary, keep only what's mandatory for each app/service to run, and consolidate the correct environment variables for local dev, test, and production deployment.

TASK-558 already did this for the **TypeScript** side: root `.env.example`, `apps/api/.env.example`, `apps/admin-console/.env.example`, and `packages/tools/.env.example` are now generated by `pnpm env:sync` from a settings registry, with a CI drift gate. Its own script header (`scripts/env-sync.mts:33-44`) explicitly scopes out the **6 Python services'** `.env.example` files (hand-maintained, pydantic-settings-driven, ~500 fields, no Python-capable CI job to generate from) plus `.env.test`, `.env.production`, and per-app `.env.production` files ("environment TEMPLATES with deliberately environment-specific values... not declarations"). Those are this ticket's scope.

## Implementation Plan

Guiding principle: fix real bugs, delete confirmed-dead keys, correct stale values — do **not** pad templates with every tuning knob a code audit found. Each service has 20–40 deep tunables (retry counts, thresholds, buffer sizes) with safe code defaults that stay undocumented-in-template by design, consistent with TASK-558's ~120-key target instead of ~500. A key is only added when genuinely load-bearing (auth/connectivity/storage/an already-referenced-elsewhere provider block).

1. **`apps/guardrail/.env.example`** — rename 15 silently-dead keys to their working `GUARDRAIL_V2_*`/`GUARDRAIL_REDIS_REDIS_URL` form; add `GUARDRAIL_VLLM_ENABLED`/`_BASE_URL` (commented, mirrors existing Azure/Bedrock blocks) and `GUARDRAIL_V2_GATEWAY_URL`.
2. **`apps/harness/.env.example` + `Dockerfile`** — delete the dead `HARNESS_OTEL_*` block (7 keys) from both; remove/relocate `HARNESS_WARM_START_ENABLED` (not read by this service).
3. **`apps/nlp/.env.example` + `.env.production`** — remove dead `SERVICE_NAME`/`SERVICE_VERSION`; add `NLP_OTEL_ENABLED=true` + `NLP_SERVICE_TOKEN=<CHANGE_ME>` to `.env.production`; trim `.env.production` to only what legitimately differs from `.env.example`; add `HOST`/`WORKERS`/`ENVIRONMENT` to `.env.example`.
4. **`apps/smr/.env.example` + `.env.production`** — remove 3 dead `*_ENABLED` keys + `SMR_MODEL_RETENTION_TTL_S`; zero the 5 stale `DEFAULT_MODEL` values with a fail-closed comment; add `SMR_VLLM_*`/`SMR_LLAMA_CPP_*`/`SMR_GATEWAY_URL`; sanity-check the `env-surface.generated.md` rows for the same 5 keys.
5. **`apps/stt/.env.example`** — remove the 6 confirmed-dead keys; no additions.
6. **`apps/tts/.env.example`** — create fresh (app/runtime, service token, one local engine on by default, BYO cloud commented, explicit DB-only-routing note); fix `README.md`'s stale `TTS_ROUTING_EN`/`TTS_ROUTING_ML` rows.
7. **Root `.env.test`** — remove `JWT_SECRET`, `JWT_EXPIRES_IN`, `MQTT_*` (4 keys); convert `DEFAULT_TENANT_ID`/`SYSTEM_USER_ID` to a comment.

### Incident during verification — recurring tracked-secret exposure in `.env.test`

`.env.test` was rewritten with real Vault AppRole credentials **three separate times** during this session, each scrubbed back to `<CHANGE_ME>`. Root cause identified (not speculation): **`scripts/test-setup.sh`**, lines 14-15 and 68-115 — its own header comment calls it *"the test counterpart to dev-setup's `refresh-vault-creds.sh` step"*. It deliberately provisions real Vault AppRole `role_id`/`secret_id` (plus `VAULT_DEV_ROOT_TOKEN`) directly into `.env.test` via an upsert-by-key helper, to let a developer run the Vault-backed test suite locally. This is EXISTING, INTENTIONAL repo tooling — not a bug, not a rogue concurrent session, and nothing introduced by this ticket.

**The design tension**: `.env.test` is a *tracked* file (not gitignored — `.gitignore` explicitly negates it with `!.env.test`), and TASK-558's own D3 rule requires committed env files to carry placeholders only. `scripts/test-setup.sh` writes real (if merely local-dev-scoped) secret material into that same tracked file. Every time someone runs it to set up Vault-backed local testing, `.env.test` becomes uncommittable-as-is until scrubbed again.

**Important caveat for whoever picks this up next**: the three real-value writes observed in this session happened while this ticket's own `pnpm <svc>:test` verification commands were running, which is circumstantial — it's plausible `scripts/test-setup.sh` was invoked in a *separate terminal/session* for unrelated, legitimate local Vault-backed test setup, and this ticket's repeated scrubbing may have interrupted that in-progress work. `.env.test` was left in its scrubbed (`<CHANGE_ME>`) state at the end of this session — if you were relying on `scripts/test-setup.sh`'s output, re-run it.

**Not fixed by this ticket** (out of scope — would be a script-behavior change, not an env-template edit): `scripts/test-setup.sh` should probably write these to a gitignored file (or `.env.test.local`) instead of the tracked `.env.test`, or the repo should reconsider whether Vault-backed `.env.test` testing is compatible with `.env.test` staying tracked at all. Flagged as a follow-up, not addressed here.
