## A. How STT works today (per the architecture docs)

### Realtime (live consultation transcription) — `docs/architecture/overview.md` §3.1

Verified there against `apps/api/src/modules/streaming/`, `packages/applications/src/services/stt/streaming/`, `apps/stt/src/stt/streaming/`:

1. SDK opens a consultation (`POST /api/v1/consultations/open`) and starts recording (`POST /api/v1/consultations/:id/recording/start`).
2. `POST /api/v1/audio/transcription-jobs/stream/session` → gateway creates an STT session (`POST /internal/streaming/sessions`) and returns a `sessionId` + one-time stream ticket (minted via `POST /api/v1/auth/stream-ticket`).
3. SDK opens `WS /ws/stt/stream?sessionId&ticket`. All handshake failures close with generic code `4401`.
4. Client-side pipeline (room → noise-filter → VAD) sends binary PCM frames; gateway `XADD`s to `stt:audio:{sessionId}`; STT reads, runs VAD/ASR/diarization, `XADD`s to `stt:result:{sessionId}`; gateway relays partial/final transcripts back over the WS with a seq number + a 200-message resume buffer, applying egress backpressure (drop partials, queue finals) above a 512 KiB WS buffer watermark.
5. `LiveDocumentationService` also subscribes to `stt:result`, debounces final segments (3 segments or 5 s idle, kill switch `LIVE_DOC_ENABLED`), calls SMR for a running SOAP note and NLP for entities, republishes over `SSE GET /consultations/:id/live-summary/stream`.
6. STT calls back into the gateway's internal surface (`/api/v1/internal/stt/*`) for transcripts, job lifecycle, audio-records, media, authenticated by service token.
7. `POST recording/stop` ends the STT session and persists a `TRANSCRIPT` `ContextItem` + `AudioRecording`.

### Batch — §3.2

`POST /api/v1/audio/transcription-jobs` (single/batch/streaming variants) creates `TranscriptionJob` rows; the STT Dramatiq worker (broker Redis DB 5) pulls audio from the MinIO `recordings` bucket, transcribes, and reports lifecycle via `/api/v1/internal/stt/jobs/:id/{start,progress,complete,fail}`; status streams via `SSE GET /audio/transcription-jobs/:id/stream`.

### Voice profile enrollment — §3.5

`POST /api/v1/voice-profile/enroll` → STT `POST /internal/voice-profile` → speaker embedding upserted; `UserVoiceProfile` row tracks state; diarization matches enrolled profiles during live sessions.

**Note a discrepancy**: §3.5 and the "Backing infrastructure" table describe the speaker embedding as stored in **Qdrant** (`stt_speaker_embeddings`). This contradicts `apps/stt/README.md`'s explicit callout (see §E below) that the Qdrant speaker store was **removed by design** in TASK-330 — current diarization is in-memory/session-scoped, with cross-session identity from **PostgreSQL** voice profiles only.

## C. Prior research conclusions — `docs/research/ai-ml/`

Exactly two files exist in this directory (sibling dirs `security/`, `networking/`, `architecture/`, `configs/`, `clinical-harness/`, `infrastructure/`, `deployments/` exist but are out of the requested `ai-ml` scope):

**1. `whisper-onnx-apple-silicon-best-practices.md`** (dated 2026-02-08, 742 lines, cites `apps/stt/src/stt/models/onnx_loader.py` and `batch_service.py` directly as "your codebase"):
- Whisper's feature extractor has a **hard 30 s window**; recommends manual chunking (`chunk_length_s=30`, `stride_length_s≈5s`) over the pipeline API for long audio.
- CoreML execution provider config for Apple Silicon: `MLComputeUnits="ALL"`, `ModelFormat="MLProgram"`, `intra_op_num_threads=0` (auto).
- Quantization guidance: use `q4` for CPU/CoreML, avoid fp16 on CPU.

**2. `whisper-onnx-optimum-inference-optimization-2025.md`** (dated 2026-02-12, 305 lines):
- VAD-first + segment-merging before inference is standard practice (each `generate()` call carries ~6 s fixed encoder+decoder overhead on CPU); warns that `merge_segments` can corrupt timestamps if not bounded.
- Batched inference via `ORTModelForSpeechSeq2Seq` requires explicitly passing `attention_mask` (a documented Transformers bug, issue #32228, otherwise silently mis-handles it).
- **faster-whisper (CTranslate2) vs Optimum ONNX**: faster-whisper is "often ~4× faster" and "widely used in production"; the doc's explicit recommendation is to use faster-whisper when latency/throughput is the priority. This is directly relevant background for TASK-472 — it confirms the codebase's existing choice of `FasterWhisperAsrAdapter` (verified in TASK-451/456/472's Current State sections) was already the researched, correct call for the batch/CPU case; it does **not** address the streaming-native-transducer question TASK-472 raises, since neither faster-whisper nor Optimum ONNX is a streaming-native decoder.

Both documents are scoped to **batch/offline** Whisper inference tuning — neither touches the realtime streaming hot path, commit policy, VAD onset, diarization, or endpointing that the 16 SOTA tickets address. There is no direct duplication risk between this research and the ticket track; it is background context for TASK-472 only.
