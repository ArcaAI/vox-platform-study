## Requirement Analysis

Temporal records **every** activity input and output — plus the workflow input and every signal — into an immutable **workflow history** that is replayed on every worker pickup. The history has a hard **size budget (~50 MB)** and a per-payload gRPC ceiling; a run that pushes large blobs through many activities marches toward both. The harness workflow does exactly that, and a **regen loop** multiplies it.

The large blobs, all inline today (code-verified below), are the transcript, the assembled prompt, the generated note, and the RAG chunk texts. Each is recorded **once as an activity result and again as the next activity's input**, and the whole assemble→generate→extract→sensors chain re-runs on **each** bounded-regen iteration and each optimistic-assurance edit. On a long encounter with several regens, the same transcript + note are serialized into history a dozen-plus times.

The fix is the standard Temporal **claim-check pattern**: store the blob **out-of-band** (self-hosted MinIO or Redis) and pass a small **reference** (bucket/key/size/sha) through the workflow instead. Activities dereference the ref at the edge; the workflow only ever holds the small ref, so history stays flat regardless of transcript/note length or regen count. `continue_as_new` is explicitly **not** the fix (TASK-448 S3: ~7 years to the ~51,200-event cap — event *count* is not the pressure; payload *size* is), and the terminal-abandon timer already shipped in TASK-458 — this ticket is the **remaining size-budget hardening only**.

The load-bearing constraint is **replay safety**: a payload-shape change must not break workflows started before it (they replay old histories with inline blobs) or new ones. The design keeps the inline fields, adds optional ref fields, resolves inline-or-ref inside activities, and threads only data — the same additive-optional, no-`patched()` posture the codebase already uses for `phi_enabled` (TASK-357) and `prior_verdicts` (TASK-359 WS-1).

### Acceptance criteria

- [ ] **AC-1 (claim-check core, hermetic RED→GREEN)** — `store_blob(text)` returns a `ClaimCheckRef` and `load_blob(ref)` round-trips it byte-identically against a **fake in-memory store** (no live MinIO); the key is content-addressed (sha256) and deterministic; a test proves round-trip fidelity. RED: module absent.
- [ ] **AC-2 (threshold gate)** — `should_offload` leaves strings **below** `HARNESS_CLAIM_CHECK_MIN_BYTES` inline (small prompts/notes never hit the store) and offloads those above it; the boundary is tested. Prevents a store round-trip tax on tiny payloads.
- [ ] **AC-3 (activities resolve inline-or-ref)** — each big-payload activity accepts **either** the inline field (old shape) **or** the `*_ref` (new shape) and produces the offloaded form above threshold; a test drives an activity with an inline input and with a ref input and asserts identical materialized behavior. This is the backward-compat seam.
- [ ] **AC-4 (replay-compat — the E4 crux)** — a **captured pre-483 workflow history** (inline transcript/note blobs) **replays GREEN** under the new worker code, AND a **new-run history** (refs) replays GREEN — both via `test_replay_compat`. In the preferred additive-optional design **no `workflow.patched()` marker and no new command** are introduced (proven: the history's command sequence is unchanged); if the implementation is forced to add a store/load *command*, it is gated behind `workflow.patched("task-483-claim-check")` with a NEW captured fixture and both branches replay. (See §Replay safety.)
- [ ] **AC-5 (history stays flat — the point)** — a test/estimate shows that a multi-regen run's recorded history size is **bounded by the ref count, not the blob size** — i.e. doubling the transcript/note length does not grow history materially once offloaded (the size-budget protection the ticket exists for).
- [ ] **AC-6 (PHI stays out of history)** — a test asserts that when a blob is offloaded, its **content never appears in the workflow history payloads** — only the `ClaimCheckRef` (bucket/key/sha, no PHI) does. The blob lives in the self-hosted store with a TTL; no clinical text is serialized into Temporal history for offloaded fields.
- [ ] **AC-7 (self-hosted store, fail-closed config)** — the store is MinIO (S3-compatible, self-hosted) or Redis; MinIO creds are `SecretStr` via `HARNESS_`-prefixed config validated at startup; no cloud egress. `uv lock` re-run if a client dep was added.
- [ ] **AC-8 (gates)** — `pnpm py:harness:test` (hermetic — Temporal/LLM/NLP stubbed, store faked) + `py:harness:lint` + `py:harness:typecheck` green, **including the replay-compat suite**. Output pasted into §Implementation Summary. Zero diff outside the manifest; no apps/api / Prisma change.

### Non-goals

- **`continue_as_new`** — explicitly **not** needed (TASK-448 S3: ~7 years to the event-count cap; the pressure is payload *size*, not event *count*). Do not add it.
- **The terminal-abandon / edit-rerun cap** — already shipped in [TASK-458](../TASK-458-Harness-Idempotency-Escalation/README.md) (C1-02, `task-458-gate-terminal-abandon` / `task-458-edit-rerun-cap`). Do not re-open or disturb those markers.
- **Worker Versioning migration** — TASK-448 notes "prefer Worker Versioning over further `patched()` accretion" as a *general* direction; adopting it is a separate strategic ticket, not this one. This ticket adds **at most one** `patched()` marker (and prefers **zero**).
- **Moving the durable persistence out-of-band** — the `ContextItem`/`NamedEntity`/`SummaryMeta` DB writes and the apps/api internal callbacks are unchanged; claim-check is confined to the **Temporal-history** payload plumbing (activities dereference before persisting).
- **A cloud object store** — self-hosted MinIO/Redis only (track guardrail; the blobs are clinical transcripts/notes).
- **Compressing or encrypting the inline fields as an alternative** — the claim-check pattern (out-of-band + ref) is the chosen approach; inline compression does not bound history growth under regen multiplication.

## Replay safety (the E4 discipline — read before coding)

Temporal replays a workflow by re-executing its code against the recorded history and asserting the **command sequence** matches. Two rules govern this change:

1. **Preferred design — additive-optional, no marker.** Keep every inline field; add the optional `*_ref` field with a safe default; do the `store_blob`/`load_blob` **inside the existing activities** (side effects belong in activities, never the workflow). The workflow only threads a small ref, reconstructed deterministically from recorded activity outputs on replay. This adds **no new `execute_activity` command**, so — exactly like `phi_enabled` and `prior_verdicts` — it needs **no `workflow.patched()` marker**. Old in-flight histories carry the inline blob in the old field; the resolve-**inline-or-ref** logic in each activity handles both (ref set → dereference; ref absent → use inline). New runs populate the ref. `test_replay_compat` proves both a pre-483 (inline) fixture and a new-run (ref) fixture replay GREEN.

2. **Fallback — new command, gated.** If (and only if) the implementation cannot fold store/load into the existing activities and must add a **distinct** `store_blob`/`load_blob` **activity invoked from `workflows.py`**, that adds a command to the sequence and **REQUIRES** `workflow.patched("task-483-claim-check")` + a NEW captured replay fixture, so pre-483 histories (marker absent → `patched()` False → legacy inline path) and post-483 histories (marker present → claim-check path) both replay. This is the TASK-458 C1-02 pattern. **Prefer design 1**; take design 2 only with an explicit STOP-and-report first.

Either way, the replay-compat tests are a **hard gate** (per `06-python-services.md`: "Workflow code changes must keep replay compatibility — run the replay-compat tests before shipping changes to `workflows.py`").
