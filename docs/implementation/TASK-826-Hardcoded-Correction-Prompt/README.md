## 1. The defect

`_CORRECTION_SYSTEM_PROMPT` (`apps/harness/src/harness/temporal/interpreter/nodes/consultation_realtime.py:561`,
used at `:663`) is a **Python constant**. `consultation.proposeCorrections` — the durable note-level
corrector — runs on it.

Its realtime sibling `agent.grammar`, added by TASK-815 Lane R, resolves a governed, approved,
version-pinned `PromptTemplate` through the node's `promptTemplateId` binding and **degrades visibly**
when unbound.

So two nodes performing the same class of work have opposite configuration postures, and the older
one violates the project rule: *"an engine name, model id, endpoint, credential, threshold, **prompt**,
taxonomy or label set is NOT a literal in code"* (`.claude/rules/00-project-context.md`
§Configuration Principles).

## 2. Why it matters beyond tidiness
A tenant cannot change how their notes are corrected, cannot review the instruction, and cannot pin a
version — while the *same capability* on the realtime lane is fully governed. A reviewer comparing
the two would reasonably conclude the platform's prompt governance is inconsistent, and be right.

## 3. What closing it requires
- Resolve the prompt through the same governed path `agent.grammar` uses (bound `promptTemplateId`,
  APPROVED, version-pinned), with **no in-code fallback** — an unbound or unapproved template degrades
  visibly rather than silently substituting a literal.
- Seed the platform-default template as a **SYSTEM-tenant** row, the sanctioned platform tier, as
  TASK-815 Lane N did for the findings and grounding instructions.
- A test proving a default fallback CANNOT creep back — Lane N's shape: adding one turns the
  "unbound instruction degrades and never falls back" test red.

## 4. Definition of Done
- [x] `_CORRECTION_SYSTEM_PROMPT` deleted; the prompt resolves through the governed template path
- [x] Platform default seeded as a SYSTEM-tenant `PromptTemplate` (`71000000-…-044`)
- [x] Unbound/unapproved degrades visibly; two mutations prove no fallback can return (§5e)
- [x] Cross-language parity held; seeds regenerated by script (`registryChecksum` unchanged)

## 5. Implementation Summary

### 5a. The brief was right about the defect and half wrong about the model to copy

The brief said *"its realtime sibling `agent.grammar` resolves a governed, approved,
version-pinned `PromptTemplate`"*. True — but **not in Python**. `agent.grammar` has TWO
implementations and they had opposite postures:

| | Where | Posture before this ticket |
|---|---|---|
| Realtime executor (the one that actually runs it) | `LiveDocumentationService.resolveGovernedNodePrompt` (TS) | Governed. Resolves APPROVED, throws when unbound. |
| Durable wrapper (dispatchability only) | `interpreter_agent_grammar` → **delegates to `interpreter_consultation_propose_corrections`** | The hardcoded literal, because it is the SAME engine. |

So the governed path to copy was `_llm_policy.resolve_instruction` (Lane N's, used by
`agent.important_findings` and `guard.groundedness`), not anything `agent.grammar`'s own Python
wrapper does. Fixing the engine fixed both names at once, which is exactly what the delegation
design in `agent_catalogue.py` exists to buy.

### 5b. No schema change, no checksum move — confirmed, not assumed

`consultation.proposeCorrections`'s config schema already spreads `PROMPT_BINDING_PROPERTIES`
(`node-config-schemas.ts:822`), so `promptTemplateId` / `promptVersionNumber` / `evalGate` were
already declared and validated. Nothing in `node-registry.ts` or `node-config-schemas.ts` was
touched.

`registryChecksum()` hashes `WORKFLOW_NODE_REGISTRY`'s descriptors and nothing else
(`node-registry.ts:1308`), so it **could not** move. The regen script printed it unchanged:
`21901af1becbe9a9be072bab9eac6a5fe97f13c1de1f370b591c2f8da549b2d4`. The two GRAPH checksums did
move, as they must — the authored graphs now carry the binding. This is TASK-821's case (seeding
an instance of an already-registered type), not TASK-815's.

### 5d. Two decisions worth stating

**The instruction resolves BEFORE detection, not after the "no entities" early return.**
Configuration validity is not conditional on what the detector happened to find. Resolving later
would let an unbound node report `SUCCEEDED` with zero proposals on every quiet run —
indistinguishable from a working one, and the "runs for nobody" failure TASK-815 §14a names.

**`resolve_instruction` takes an `api` parameter.** `_llm_policy`'s own docstring explains why
each module binds its own client accessors: they are what its tests redirect. A helper closing
over `_llm_policy._api_client` would be unpatchable from `consultation_realtime`'s suite, and in
production one activity would resolve its selection through one client object and its instruction
through another. The parameter keeps ONE approval bar with each module's own accessor.

**A SEPARATE template body from `LIVE_GRAMMAR_SYSTEM` (…043).** The live pass reviews a PARTIAL
transcript, so its body says *"do not correct a word that is merely cut off at the end"*. The
durable pass is fed from `n_synth` — a FINISHED note — where that caveat would suppress a genuine
error at the end of the note. One instruction cannot be right about both; a seed test asserts the
two bodies differ on exactly that point.

### 5e. Mutation evidence — no fallback can return

Two mutations, both against `consultation_realtime.py`:

1. **The deleted literal, restored verbatim** as an `except InstructionUnavailable` fallback →
   **4 RED**: `test_an_unbound_instruction_DEGRADES_and_never_falls_back_to_a_default`,
   `test_an_unapproved_instruction_DEGRADES`, `test_a_missing_template_DEGRADES`,
   `test_the_module_holds_no_correction_prompt_literal`.
2. **A fallback carrying none of the literal's giveaway phrases**

   mutation: the behavioural tests, not the grep, are what hold the line.

Both mutations reverted; the suite is green.

## 6. What the lane found that the ticket had wrong

**`agent.grammar` does NOT resolve a governed prompt in Python.** The ticket (and the orchestrator's
brief) framed this as two nodes with opposite postures. In Python they are the same code:
`interpreter_agent_grammar` **delegates to `interpreter_consultation_propose_corrections`** — the very
function carrying the literal. Its own docstring states the design: *"two names for one capability are
safe only when there is one implementation behind them."* The governed implementation is the
**TypeScript** realtime executor (`LiveDocumentationService.resolveGovernedNodePrompt`).

So the model to copy was Lane N's `_llm_policy.resolve_instruction`, not `agent.grammar`'s Python
side — and fixing the engine fixed both names at once, which is what the delegation buys.
