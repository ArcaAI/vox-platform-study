## 1. Requirement Analysis

Seeded, live `PromptTemplate` rows instruct the LLM to free-write ICD-10 diagnosis codes directly
into note prose, with no tool verification. The one mechanism built to catch this — MCP
`validate_codes` — runs post-hoc (after persistence), is opt-in
(`mcp_tools_enabled`), and has **no terminology server registered in any deployment**, so in
practice it never fires. A deterministic, non-hallucinating linker
(`apps/nlp/src/nlp/services/ontology_linker.py`, an offline ~40-term dictionary: exact match or
`None`, never a guess) exists on the default path but is out of scope for this ticket — it is
neither modified nor extended here; it is cited only as the eventual code source once prompts stop
inviting the model to author codes itself.

**Re-verification against the live tree surfaced materially larger scope than the ticket brief
that seeded this program** (which named only `seed/07-prompt-template.ts`). Two independent seed
sources instruct code emission:

1. **The base catalog** — `packages/database/src/prisma/db_main/seed/07-prompt-template.ts` — 12
   distinct `PromptTemplate` rows (the platform-default SOAP template + 11 department-specific
   templates) plus the SOAP structured-output JSON-schema's field description, applying to
   `DEFAULT_TENANT_ID` (`50000000-0000-0000-0000-000000000000`) and inherited by any tenant with
   no department-specific override.
2. **The ArcaAI clinical prompt library** — `packages/database/src/prisma/db_main/seed/07b-arcaai-clinical-content{,-v2,-v3}.ts`
   (content) + `07b-arcaai-clinical-templates.ts` (wiring) — **22 department × visit-type SUMMARY
   templates**, seeded for the ArcaAI production day-1 tenant (`SEED_CUSTOMER_TENANT_IDS.ARCAAI`)
   and currently pinned to `ARCAAI_CLINICAL_APPROVED_VERSION = 3`
   (`07b-arcaai-clinical-templates.ts:537`) — i.e. **this is the corpus the tenant that matters
   most (harness-enabled, DNA-enabled per `TASK-700`) actually runs today.** Unlike the base
   catalog, this corpus's v3 wording already carries a real anti-hallucination clause on most
   occurrences ("Record a code only if the clinician stated one" / "...stated it") — a genuine,
   deliberate mitigation the original assessment did not have visibility into (it is generated
   content in a 348 KB file, not something a `file:line` grep-only pass would surface easily).
   That mitigation is real but insufficient against the register invariant: INV-065/066 require
   **no code without a tool-verified match**, and "the clinician said it aloud" is not a
   verification — the model can still mishear or misremember the exact code value while believing
   it is transcribing what was said. This ticket closes that gap too, not just the base catalog's
   unconstrained instructions.

Register invariants (`01-invariant-register.md`, category `terminology`) this ticket satisfies:

| INV | Statement |
|---|---|
| INV-065 / INV-066 | No code must be emitted without a tool-verified match; hallucinated codes are strictly forbidden |
| INV-071 | No guessed terminology must be inserted into the work note or final record |
| INV-231 | No clinical code may be free-generated by the model into the note or a write payload |
| INV-233 | Unmatched terms must be flagged unmapped for human review; no guessed code must be inserted |
| INV-373 | Note composer may show a bound code as structured data, not free-generated digits |
| INV-432 / INV-449 | No hallucinated code must exist in the note or write payload; low-confidence/unmapped concepts stay unmapped rather than becoming guessed codes |

**Explicitly OUT of scope:**

- Making the MCP `validate_codes` mechanism gating, pre-persistence, or registering a terminology
  server — that is a separate, larger change (harness/MCP infrastructure), not a seed-content edit.
- Extending `ontology_linker.py`'s coverage beyond its current ~40 terms.
- `07b-arcaai-clinical-templates.ts`'s versioning/wiring mechanics themselves (the
  `ARCAAI_CLINICAL_APPROVED_VERSION` pin, the `PromptVersion` history discipline) — this ticket
  uses that mechanism as-is (adds a new approved version), it does not redesign it.
- Any change to `packages/database/scripts/generate-arcaai-clinical-content-v2.mjs` /
  `-v3.mjs` — those generator scripts read from an external, out-of-repo source markdown
  (`readFileSync('/Users/.../Downloads/v3/DEPARTMENT_PROMPTS_v3.md', ...)`) that does not exist in
  this repository; they cannot be re-run to regenerate a fix. This ticket hand/script-edits the
  already-generated, committed `.ts` output directly (see Task 3).

Each content file defines one `export const <DEPT>_<VISIT>_CONTENT_V{1,2,3}` per template, as one
long template-literal string (real embedded newlines, not `\n` escapes) — e.g.
`07b-arcaai-clinical-content-v3.ts:84` (`SURGERY_NEW_REFERRAL_CONTENT_V3`) through `:147`
(`SURGICAL_ONCOLOGY_FOLLOWUP_CONTENT_V3`); `PRE_SUMMARY_CONTENT_V3` at `:150` has no ICD-10 hit
(confirmed by direct scan — the pre-summary heading set has no assessment/diagnosis section).
Sample verified clauses (v3; representative, not exhaustive — full inventory is Task 1's output):

```
- Confirmed or working diagnosis with ICD-10 code(s).\n    - Record a code only where...
- Include **ICD-10 code(s)** only if the clinician stated one, in order of likelihood...
- Working diagnosis/differentials; ICD-10 if stated\n   - Record only the diagnos[is]...
- No invented identifier, ICD-10 code, drug, dose, value, date, score or...
```

The recurring "Record a code only if the clinician stated it" clause is a genuine, deliberate
mitigation absent from the base catalog (§2.1) — it materially reduces (but does not eliminate)
hallucination risk, since the model is still the one deciding whether "the clinician stated it" and
still free-writing the digits with no tool cross-check. Per INV-065/066 this remains a violation:
the requirement is a *tool-verified match*, not *model-asserted transcription fidelity*.

### 2.3 What already exists and must be REUSED

- **The versioning/history discipline for ArcaAI templates already exists and is the correct
  mechanism for this fix** — `ARCAAI_CLINICAL_SEEDED_VERSIONS`, `V2_CONTENT_BY_TEMPLATE_ID` /
  `V3_CONTENT_BY_TEMPLATE_ID`, `VERSION_CHANGE_REASON`, `ARCAAI_CLINICAL_VERSIONS` (all in
  `07b-arcaai-clinical-templates.ts:463-628`). Adding a v4 corpus and bumping
  `ARCAAI_CLINICAL_APPROVED_VERSION` is the same pattern already used to ship v2 and v3 — reuse it
  rather than mutating v3's content in place (mutating in place loses the diffable rollback
  property the file's own module comment, `:26-33`, explicitly values).
- **The base catalog's `extraVersions` pattern** (`07-prompt-template.ts:2360-2410`) for adding a
  new `PromptVersion` history row without discarding the old one.
- **The data-migration exemplar**: `packages/database/scripts/clear-stale-pre-summary-overrides.ts`
  — dry-run-by-default, `--apply` to write, single transaction, idempotent (a second run finds
  zero rows), pre-flight printout before any write, `getPlatformAdminPrismaClient_Unscoped` (the
  lint-allow-listed unscoped client for `packages/database/scripts/**`). This is the pattern Task 4
  follows.
- **`PromptTemplate.approvedVersionNumber`** (`prompt-template.prisma:71`) is how a template pins to
  a specific `PromptVersion` snapshot rather than the mutable `content` column — the resolver
  serves the pinned snapshot (`PromptResolutionService.resolveGovernedContent`, per
  `07b-arcaai-clinical-templates.ts:28-30`'s own comment). The migration task must set this, not
  just `content`, for parity with how the seed itself is structured.

## 3. Knowledge & Best Practices

- **`.claude/rules/02-database-prisma.md`** — seed edits are hand-authored TS, not Prisma
  migrations; no schema change is needed here (`PromptTemplate`/`PromptVersion` already have every
  column this ticket needs).
- **`.claude/rules/01-development-workflow.md`** TDD ordering — Task 1 (golden test, RED) precedes
  every content edit.
- **Karpathy guideline #3 (surgical changes)**: the base-catalog edits (Task 2) are genuinely
  surgical — 13 discrete, hand-reviewable locations. The ArcaAI corpus (Task 3) is NOT
  hand-editable at that granularity (66 long-string constants across three 300+ KB files) —
  the plan therefore uses a small, assertion-guarded script (mirroring the rigor of the existing
  `generate-arcaai-clinical-content-v3.mjs`, which asserts exact section counts and throws on any
  mismatch) rather than either a blind `sed` or 66 manual edits. This is the "simplest thing that
  correctly solves the problem at this scale," not gold-plating.
- **`docs/development-patterns-and-standards.md`** / `04-application-services.md`'s DTO
  discipline doesn't apply here — this ticket touches seed content and a migration script, not a
  request/response DTO.
- **Known pitfall specific to this ticket**: the seed's `promptTemplate.upsert` in
  `07b-arcaai-clinical-templates.ts:668-673` (`update: data, create: data`) means a **fresh seed
  run on an empty/reset dev DB always gets the fixed content** — but a database where the seed
  already ran once (staging, prod, or any long-lived dev DB not periodically `db push
  --force-reset`) keeps its already-persisted row content until something explicitly re-writes it.
  This is exactly why Task 4 (the data migration) exists — re-running `pnpm db:seed` is not itself
  a safe or sufficient fix for a deployed environment, both because seeds are not the deploy
  mechanism for staging/prod (`09-infrastructure-devops.md`: migrations are the prod path, not
  `db push`) and because a blind re-seed of `promptTemplate.upsert` would silently clobber any
  tenant-customized row at the same id.
- **Anti-pattern avoided**: do not touch `apps/nlp/src/nlp/services/ontology_linker.py` under this
  ticket — it is explicitly out of scope (§1) and touching it would blur this ticket's containment
  scope with the larger MCP-terminology-validation architecture work.

### Task 4 — Data migration for deployed rows
- **Agent:** T3 · sonnet-5 · medium
- **Files:** new `packages/database/scripts/migrate-icd10-prompt-instructions.ts`
- **Approach:** Follow `clear-stale-pre-summary-overrides.ts`'s exemplar structure exactly
  (dry-run-by-default, `--apply` to write, single transaction, idempotent, pre-flight printout,
  `getPlatformAdminPrismaClient_Unscoped`). For each of the known seed template ids (the 13 base-
  catalog ids from §2.1 + the 22 `ARCAAI_CLINICAL_TEMPLATE_IDS` from §2.2 — all deterministic
  constants, importable from the seed files):
  1. Load the row's CURRENT `content` (and, for versioned rows, the currently-`approvedVersionNumber`-pinned
     `PromptVersion.content`) from the target database.
  2. Compute a fingerprint of the KNOWN-BAD content this ticket's fix replaces (the exact
     pre-fix strings captured in Tasks 2-3, or their SHA-256 hashes, computed by those tasks and
     exported as constants both the seed AND this migration script import — single source of
     truth, no copy-paste drift between "what the seed now says" and "what the migration checks
     against").
  3. If the deployed row's content matches the known-bad fingerprint (unmodified since seeding),
     safely apply the fixed content: insert a new `PromptVersion` row + update
     `PromptTemplate.content`/`currentVersionNumber`/`approvedVersionNumber`, exactly mirroring
     what the seed now does, inside the transaction.
  4. If the deployed row's content does NOT match the known-bad fingerprint (i.e. a tenant admin
     has since edited it in the admin console), **do not overwrite it** — log it to the pre-flight
     report as "DRIFTED — needs manual review" and skip. This is the human-gated portion: a
     tenant-customized row must not be silently overwritten, and reviewing what a tenant customized
     their prompt to say is a business decision the executing agent should not make unilaterally.
  5. Print a summary: rows fixed, rows already-fixed (idempotent no-op), rows skipped-as-drifted
     (with their ids for follow-up), rows not found (already deleted).

## 9. Owner Decision 2026-08-17 — all versions allowed, v3 is the default

`docs/architecture/agentic-workflow-platform/owner-decisions-2026-08-17.md` §2, row 702:

> "**Allow all current prompt versions.** v3 becomes the default at go-live. The v1
>  sign-off blocker is dissolved."

This **resolves** §7 Deviation 2 and the §6 open questions rather than deferring them —
but it resolves them in the *opposite* direction to what Deviation 2 assumed. Deviation 2
treated v1's unfixed ICD-10 wording as debt awaiting clinical sign-off. It is not debt:
v1 is a **byte-exact port of the running v1 production deployment**, deliberately frozen,
and the owner has now confirmed it stays selectable as-is. Nothing about v1 needs to
change. What needed to change is that the *intent* was implicit — nothing in the tree
said "v3 is the default" or stopped that from quietly becoming false.

### 9.1 Current state — established, not assumed (2026-08-17)

| Fact | Evidence |
|---|---|
| v2 and v3 are clean of ICD-10 wording | `grep -c 'ICD-10\|ICD10'` → `0` on `07b-arcaai-clinical-content-v2.ts` and `-v3.ts` |
| v1 still carries it, in 10 of 23 bodies | same grep → `10` on `07b-arcaai-clinical-content.ts` |

So the fixture is already consistent with what is served, for the strongest possible
reason: the content it pins is unmodified.

### 9.2 The residual clinical-safety consideration, stated plainly

**All versions allowed + v1 still instructs code authoring = a version that violates
INV-065/066 remains reachable.** That is a real consideration and it is not hypothetical:
`ARCAAI_CLINICAL_APPROVED_VERSION = 1` is a one-line change, and
`PromptTemplate.approvedVersionNumber` is editable from the admin console.

The v1 wording was **not** silently changed — the owner decision explicitly keeps all
versions, and v1's fixture header requires clinical/product sign-off before its hashes may
move. Instead, the distinction that matters is drawn where it belongs:

> v1 may exist. v1 may be rolled back to **on purpose**, as an explicit and auditable act.
> v1 must never become the default **silently**.

### 9.3 The guard

New: `packages/database/src/prisma/db_main/seed/__tests__/arcaai-clinical-version-policy.test.ts`
(7 tests). It asserts, in three groups:

1. **All current versions stay available** — exactly versions 1, 2, 3 are seeded; every
   version covers every template (so any pin is a complete corpus); no seeded body is empty.
2. **v3 is the go-live default** — `ARCAAI_CLINICAL_APPROVED_VERSION === 3`, and every
   template's `content`, `currentVersionNumber` **and** `approvedVersionNumber` agree with
   the pin and with the matching `PromptVersion` snapshot (the F-01/F-02 integrity path).
3. **The default may never be a code-authoring version** — asserted against *the pin*, not
   against the literal `3`, so moving the pin to 1 or 2 is what fires it. Plus a test that
   records the residual risk truthfully (v1 still has exactly 10 affected bodies, and the
   pin is not 1), which forces a deliberate update if v1 is ever cleaned.

**The guard was proven to bite** — the test passed on first run, so RED was demonstrated by
temporarily setting the pin to 1:

Honest note on ordering: this test is a **regression lock on an already-correct state**, not
a red-green driver — the product already satisfied the owner decision. The RED above is a
deliberate, reverted mutation, and is labelled as such rather than presented as TDD.
