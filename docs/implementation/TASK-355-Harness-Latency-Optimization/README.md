### 1a. About "it runs gating so many times"

The event export shows the clinician gate ran **exactly once** (one timer armed at +366 s, one `approval` signal, one `record_gate_decision`). The **regen loop also never iterated** (`generate` ×1, `run_sensors` ×1). What looks like repeated "gating" in the Temporal UI is:

- **6 × `report_progress`** activities (the TASK-345 live progress feed — stages 1–5 + terminal), each wrapped in its own activity + workflow-task event triplet;
- **~17 workflow-task `Scheduled/Started/Completed` triplets** — Temporal bookkeeping around every activity, which inflates the visible event list (115 events for 16 actual activity executions).

So there is no hidden re-gating loop to remove — but the progress feed does add ~6 workflow-task round-trips (~0.6 s total, cosmetic; see R-12).

**Conclusion: the only meaningful target is the 343.6 s inferential pass, with the 21.4 s generation second.**

## 2. Root Cause of the 344 s — anatomy of `run_inferential_sensors`

Full code review (apps/harness/src/harness/temporal/activities.py:374, sensors/inferential/*, core/llm_concurrency.py):

### 2a. 38 LLM calls (measured), all strictly serialized

| Sensor | Backend | Loop | Calls (measured run `019eb9f4…`) |
|---|---|---|---|
| `GroundednessSensor` | judge `google/gemma-4-e4b` | `for claim in claims` → 1 call/claim | **31** (claims in `citationsMap`; 12 grounded / 19 ungrounded) |
| `CitationVerifySensor` | same judge | `for claim in cited` → 1 call/cited claim | **0** (retrieval returned 0 chunks → trivial PASS) |
| `SafetySensor` | `granite-guardian-4.1-8b` | `for criterion in harm_criteria` → 1 call each | **7** (fixed default list) |

The three sensors are launched with `asyncio.gather`, **but every individual HTTP call acquires the same per-endpoint `asyncio.Semaphore(1)`** (`HARNESS_LLM_MAX_CONCURRENCY=1`, key = `http://localhost:1234`) — `core/llm_concurrency.py:116–147`. Concurrency is nominal; execution is strictly sequential: **38 calls × ~9.0 s avg = 343.6 s** (measured; decoded payload evidence in [Appendix 01 §3.7](./01-workflow-trace-analysis.md)). Production transcripts (10–50× longer than this 729-char test consult) will carry more claims — the call count scales with note size, not transcript size, but expect the higher end of `C`.

### 2b. Why each call is so slow (~9 s avg measured — for a binary yes/no)

| Cause | Detail | Where |
|---|---|---|
| **Reasoning emission not suppressed** | `HARNESS_JUDGE_SUPPRESS_REASONING=False` (unset) — gemma-4-e4b emits a full `<think>` block before the `{"supported": bool}` JSON | `eval/config.py:125`, `apps/harness/.env` |
| **`max_tokens=8192`** | ~40× overprovisioned for a 1–5-token entailment verdict; sized for the PDSQI eval judge, shared by the sensors | `eval/config.py:84` |
| **`response_format=text`** | needed for this LM Studio build, but leaves output length unconstrained | `.env` `HARNESS_JUDGE_OPENAI_COMPAT_JSON_RESPONSE_FORMAT=text` |
| **No prefix/KV cache reuse** | every call re-prefills the full transcript premise (400–1500 tokens) | serving layer |
| **No batching** | 1 claim = 1 HTTP round-trip; no cache of repeated verdicts | `groundedness.py:133`, `citation_verify.py:81` |
| **Granite loop serial** | 7 safety criteria called one-by-one inside `screen()` | `granite_client.py:100–108` |

### 2c. Worst-case amplification (regen loop)

The inferential pass re-runs after every inferential-triggered regen. With `HARNESS_MAX_REGEN=2`: worst case **3 × (21 s + 344 s) ≈ 18 minutes**. Didn't occur in the measured runs, but the tail risk scales 1:1 with whatever the single-pass cost is — another reason to crush the per-pass cost first.

Why the measured run did NOT regen despite groundedness FAIL (`decision=REGEN` label in the payload): the aggregator (`sensors/aggregator.py:55,111–119`) checks `HIGHEST_HARM_SENSORS` (entity_faithfulness, numeric_dose, safety) **before** regen-fixable sensors — and this run failed entity_faithfulness (0.474 < 1.0) and numeric_dose (0.6 < 1.0) → **FLAG outranks REGEN**, loop exits, draft goes to human review with budget untouched. Regen only fires when the *only* failures are regen-fixable (schema/coverage/citation_presence/groundedness/citation_verify).

### 2d. Where `generate` actually runs — observed config discrepancy + contention warning

`apps/harness/.env:24–25` intends `HARNESS_SMR_PROVIDER=ollama / gemma3:latest`, but the `generate` activity passes only workflow-input/policy overrides through (`activities.py:234`) — both were `null` in the measured run, so the SMR service resolved its **own** default and the response reported **`provider=lm-studio, model=default`** (1 057 tok @ 49.5 tok/s). Two consequences:

1. The dev "force Ollama" intent is **not in effect** on the workflow path (env knobs dead unless policy/input carries them) — decide which is authoritative and align.
2. In the observed dev shape, **generation shares the same LM Studio box as the judge and Granite** — raising judge concurrency (R-2) contends with `generate` and with the live-doc SMR flushes of *other concurrent consultations*. Size `Max Concurrent Predictions` accordingly and re-measure generate latency after R-2.

## 3. What the live pipeline already produces (and the harness ignores)

Review of `LiveDocumentationService` (packages/applications/src/services/consultation/live-documentation/live-documentation.service.ts) vs the harness assemble path:

| Artifact produced during the live session | Stored where | Used by harness today? |
|---|---|---|
| **LiveDoc SOAP snapshot** — running SOAP note, incrementally refined every ≥4 s flush / persisted every 30 s + on stop | `ContextItem` `type=PRE_SUMMARY`, `metaData.subType='LIVE_SOAP_SNAPSHOT'` (single upserted row) + Redis | **No** |
| Live NER (runs on the running summary, not the transcript) | SSE stream only — **not persisted** | No (and can't be, today) |
| Final transcript | `ContextItem` `type=TRANSCRIPT` | Yes |

Key asymmetry: the **legacy** summary path (`SummaryService.generateSummary`, line ~196) loads `findLatestPreSummary()` and injects it as the `{pre_summary_text}` prompt variable via `PromptAssemblyService`. The **harness** assemble endpoint (`HarnessInternalService.assemble()`, packages/applications/src/services/consultation/harness/harness-internal.service.ts:107–194) loads transcript + NER + case notes + highlights + attachments — **but never the PRE_SUMMARY**, and never populates `SummaryMeta.preSummaryIds` (the provenance field exists and is always empty on the harness path).

So during the consult we already paid for an almost-complete SOAP note, then the harness generates from scratch anyway. Feeding the snapshot in turns `generate` from cold generation into refinement (21 s → est. 4–8 s) **with zero Temporal workflow changes** — only the assemble service + prompt template.

Provenance constraints checked: sensors verify note ↔ **full final transcript** regardless of how the note was produced; attestation hashes final content; WORM `GENERATE` audit unchanged. Warm-start via prompt context is exactly what the legacy path already does. Requirement: write the consumed snapshot id into `SummaryMeta.preSummaryIds`.

Trigger dead time (recording stop → workflow start) measured at ~0.3–2.5 s — nothing to win there.

## 4. External best practices (2025–2026, sources in §9; full research with per-claim citations in [Appendix 05](./05-external-best-practices.md))

1. **Optimistic draft delivery** — the leading scribe products (Abridge: median draft 38–76 s; "Linked Evidence" per-claim verification *presented to* the reviewer, not blocking them) deliver the draft immediately and run assurance alongside human review. Nuance DAX's variant that blocked on validation *before* the clinician measurably increased after-hours work. Temporal supports this natively (parallel branch; Update-with-Start/Early Return GA since v1.28).
2. **Batched claim verification** — claim verification is NLI-style classification, the regime where batching holds: ≤ 2 pp accuracy loss through batch≈100 in 2026 studies; label-each-item JSON-array prompts (not "select the bad ones"); single-pass verifiers (VeriFastScore) report ~6.6× speedups. Safe starting point: 10–20 claims per call.
3. **Local serving is no longer concurrency-1** — LM Studio 0.4.0+ does parallel requests/continuous batching (llama.cpp engine; MLX engine since 0.4.2 with a known prefill-stall bug #1709). A dedicated `llama-server -np 4 -cb --cache-reuse 256` for judges adds prefix-KV reuse (the shared transcript premise prefill collapses; MiniCheck APC measured ~45 % saving).
4. **Purpose-built small verifiers** — MiniCheck family (0.4–7 B) achieves GPT-4-level grounded fact-checking at ~400× lower cost; Granite Guardian 3.2-5B/3.3-8B emit single Yes/No tokens (the 8B is top-3 on LLM-AggreFact). Cascade pattern: cheap screen handles ~70 %, escalate the uncertain band.
5. **Temporal hygiene** — chunked `asyncio.gather` fan-out (30–50/batch); progress via query/heartbeat-details instead of chatty activities; Local Activities only for sub-second glue (not the judge calls); speculative decoding for the *generation* model only (counterproductive for sub-4B judges).

## 7. Safety invariants (every phase must preserve)

1. Gate **never auto-PASSes**: degraded/missing sensors ⇒ FLAG / reduced-assurance, forced human review (existing aggregator semantics).
2. **Safety FLAG is never regenerated away** and (Phase D) can never be signed past: sign-off requires completed assurance.
3. All conservative-failure directions maintained: truncation/parse failure/timeout ⇒ claim **un**grounded ⇒ stricter, not looser.
4. Workflow-sequence changes ship with `workflow.patched()` gates + captured replay fixtures (TASK-348/354 discipline).
5. WORM audit truthfulness: `gate_decision` recorded only when computed; two-phase state in Phase D rather than provisional values.
