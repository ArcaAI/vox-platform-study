# Environment Configuration Reference

Introduced: 2026-07-29 (TASK-583) · Builds on TASK-558 (Environment Configuration Refactor) and TASK-582 (Python Service Env Template Hygiene) · Updated by TASK-584 (per-service naming/relocation) and TASK-585 (root `.env.example` folded into `.env.sample`, generator-owned end to end).

The one-stop reference for every environment variable HOPE reads locally: how the local files come to exist, what each service actually reads, and — the part that's easy to get wrong — **which variables are provider/model *defaults* vs. tenant *fallbacks*, and which are not env-configurable at all.**

## 1. How local env files come to exist

```
.env.sample (tracked, repo root, placeholders only)
      │
      ├── pnpm setup:dev  ──► .env.dev   (gitignored, generated, dev-shaped values)
      └── pnpm setup:test ──► .env.test  (gitignored, generated, test-shaped values + real local Vault creds)
```

| File | Tracked? | Created by | Contents |
|---|---|---|---|
| `.env.sample` | **Yes** | Generated by `pnpm env:sync` (TASK-585 — folds all 10 sections into one, CI-drift-gated end to end) | Every variable HOPE reads, dev-shaped default values, `<CHANGE_ME>` for secrets |
| `.env.dev` | No (gitignored) | `pnpm setup:dev` → `scripts/generate-env-file.sh:ensure_env_file` — copies `.env.sample` **only if `.env.dev` doesn't already exist** | Your real local dev config; `scripts/refresh-vault-creds.sh` mutates it in place with real local Vault AppRole creds |
| `.env.test` | No (gitignored, since TASK-583 — previously tracked) | `pnpm setup:test` → same helper, `mode=test` applies port/endpoint overrides, then `test-setup.sh`'s own Vault step mutates it in place | Isolated test-stack config + real local Vault AppRole creds |
| `apps/api/.env.prod` | Yes | Hand-maintained | Two labeled reference postures in one file (TASK-584): K8s ConfigMap/Secret (relocated from the former monorepo-root `.env.production`) and systemd `EnvironmentFile=` + Vault AppRole + dynamic DB creds. **Not** auto-loaded by anything; deployed processes use host env only |
| `apps/{guardrail,harness,nlp,smr,stt,tts}/.env.prod` | Yes | Hand-maintained | Per-service production reference — engine/provider connection settings relevant to that service (TASK-584) |
| `apps/*/​.env.sample` (8 deployables) | Yes | Hand-maintained (6 Python) / generated (`apps/api`, `apps/admin-console`, `packages/tools`) | Per-service reference; also folded into the root `.env.sample` (see §2) |

**Why `.env.test` changed from tracked to gitignored (TASK-583):** confirmed by reading the actual loader code — `packages/applications/src/common/env/env-file-resolution.ts` and `packages/py-env/src/hope_env/__init__.py` both skip file-loading entirely whenever `CI` is truthy, and GitLab CI sets `CI=true` by default. **CI never reads `.env.test`, tracked or not.** Meanwhile `scripts/test-setup.sh` writes real local Vault AppRole credentials into it whenever Vault-backed local testing runs — a tracked file receiving real secrets is exactly the failure mode TASK-558 already fixed once for `.env.dev`. Untracking `.env.test` closes it with zero CI impact.

**The one invariant that matters:** `ensure_env_file` (in `scripts/generate-env-file.sh`) is a no-op if the target already exists. Re-running `pnpm setup:dev`/`pnpm setup:test` never overwrites your real local secrets.

### Quick start

```bash
pnpm setup:dev      # creates .env.dev if missing, brings up dev infra + DB + Vault
pnpm setup:test     # creates .env.test if missing, brings up test infra + DB + Vault
```

Manual equivalent (if you just want the file, no infra):

```bash
cp .env.sample .env.dev
./scripts/generate-env-file.sh .env.test test
```

## 2. `.env.sample` structure

Ten sections, assembled directly by `pnpm env:sync` (TASK-585), in this order:

1. **Bootstrap floor** (generated in-process, no longer a standalone file) — `DATABASE_URL`, Vault address/AppRole, Redis, secrets provider. The only variables required *to reach the database* or *to authenticate to Vault*. Not itself "a service" — it's `.env.sample`'s first section, not a per-service one.
2. **API Gateway** (also written standalone to `apps/api/.env.sample`, generated) — the platform contract beyond the floor: downstream service URLs, shared secrets (`*_SERVICE_TOKEN`), OTel, storage, rate limiting.
3. **Admin Console** (also written standalone to `apps/admin-console/.env.sample`, generated)
4. **Code generators** (also written standalone to `packages/tools/.env.sample`, generated)
5–10. **The six Python services** (read from `apps/{guardrail,harness,nlp,smr,stt,tts}/.env.sample`, hand-maintained — content audited and cleaned up in TASK-582)

Sections 1–4 are generated straight from the settings registry; sections 5–10 are hand-maintained (same "documentation, not a contract" boundary TASK-558 drew — the CI drift gate has no Python environment to import pydantic-settings from) but still read from disk and folded in by the generator, so a change to any Python `.env.sample` is picked up the next time someone runs `pnpm env:sync`. **`.env.sample` is a fully generated artifact** — `pnpm env:sync --check` (CI job `env-drift-check`) fails if it drifts from any of the 10 sources, closing the gap the original TASK-583 hand-assembly script left open. Within the file, a key declared in more than one section keeps its FIRST active declaration; later repeats become `# [duplicate key, see <section> above] # KEY=value` comments — this is what makes "one root file, ten sources" safe to concatenate without a silent last-wins bug.

### De-duplication

46 keys are declared in more than one source file. Two different reasons, handled two different ways:

- **Intentionally shared** (e.g. `GUARDRAIL_SERVICE_TOKEN` — both `apps/api` and `apps/guardrail` need the *same* value for their shared hop) — harmless duplication, resolved by keeping one active line (first occurrence, by section order above).
- **Bare-name collisions with genuinely different per-service values** (e.g. bare `PORT`: root wants `8868` for the gateway, `apps/nlp` wants `8864` for itself, `apps/stt` wants `8861`) — only the **first** occurrence stays active; later ones are commented out with a `# [duplicate key, see ... above]` note. This is not a loss: `apps/nlp`/`apps/stt` still get their correct port when launched the normal way (`pnpm nlp:dev` / `pnpm stt:dev`), because `scripts/dev-service.sh` injects `PORT=$NLP_PORT` (etc.) as a shell-level override *before* the process reads any file — host env always wins over the file (§3 of `env-file-resolution.ts`). The commented-out line only matters if you ran that service's `uvicorn` directly, bypassing the wrapper — rare, and the comment tells you where to look.

This mirrors a defect TASK-558 already found and fixed once (`QDRANT_URL` declared twice with silent last-line-wins) — `.env.sample` never has two *active* lines for the same key.

## 3. Provider & model default / fallback semantics

**This is the part most likely to surprise you.** HOPE's policy (owner-ratified, "Provider-Plane Day-1 Defaults" program, TASK-577–581): environment variables must never select a provider or model default for *all* tenants — that's a database concern (`AiProviderConnection` / `AiTaskDefault` / `TenantTtsConfig` / `AsrPipeline`). Env keeps *connection identity* (URLs, credentials) only. Each service implements this differently; know which one you're touching.

| Service | Selection mechanism | What env vars actually do |
|---|---|---|
| **Guardrail** | DB-resolved per tenant (`AiTaskDefault` ⋈ `AiModel`), **fail-closed** (HTTP 503) if the SYSTEM selection for `guardrail.validate` is missing or a DB error occurs — no silent env fallback | `GUARDRAIL_V2_PROVIDER=lm-studio` is a **dev-only escape hatch**, consumed *only* when `GUARDRAIL_DB_CONFIG_ENABLED=false` (bypasses DB resolution entirely, for local dev without Postgres). `GUARDRAIL_{OPENAI_COMPAT,OLLAMA,AZURE,BEDROCK,VLLM,LLAMA_CPP}_*` are the connection configs for each engine that provider selector can choose among in dev-escape mode. |
| **SMR** | Tenant BYO connection first (`AiProviderConnection`, DB/Vault); if none, falls back to the service's own **platform-level** credential | `TEXT_{OPENAI,ANTHROPIC,AZURE}_API_KEY` are **platform-fallback credentials**, used only when a tenant has no enabled BYO connection for that provider — not "the platform's chosen default provider." `TEXT_*_DEFAULT_MODEL` fields are **intentionally empty** (TASK-579 — fail-closed; an unresolved model raises `ModelNotSelectedError` rather than substituting a vendor default; the field is informational only, feeding the `/providers` listing). Local engines (Ollama, OpenAI-compatible/LM Studio, vLLM, llama.cpp) gate by **presence of `base_url`**, not an `enabled` flag — there is deliberately no `TEXT_OLLAMA_ENABLED` etc. |
| **TTS** | DB-sourced (`TenantTtsConfig`), resolved by the gateway and injected per request; router **fails closed** (503, `TtsRoutingUnconfiguredError`) if no chain is injected | There is **no env routing knob at all** (TASK-577 deleted `TTS_ROUTING_EN`/`TTS_ROUTING_ML`). The SYSTEM default chain is seeded **built-in-first**: `kokoro` (English, self-hosted) / `indic_parler` (Malayalam, self-hosted). `TTS_AZURE_*` / `TTS_SARVAM_*` are tenant-BYO cloud connections only — never a platform default. |
| **STT** | DB-driven pipeline/engine selection (`AsrPipeline`); `TenantSttConfig` (TASK-567) supplies an explicit *fallback* engine (Sarvam or OpenAI) for in-session switch when the primary engine degrades | Provider credentials (`AZURE_SPEECH_KEY`, `AZURE_FOUNDRY_API_KEY`, `SARVAM_API_KEY`, `OPENAI_API_KEY`) are connection identity only; which pipeline actually runs is a DB row, not an env selector. |
| **NLP** | Model selection is **not env-configurable at all** — the gateway must inject `model_name` from the DB `AiModel` registry; fail-closed (HTTP 503) if missing or the model can't load | `*_MODEL_NAME` / `*_TOKENIZER_NAME` env vars are explicitly **filtered out** at the pydantic-settings source level (`_ModelIdentityFilteredSource`, `apps/nlp/src/nlp/core/config.py:21-74`) — setting them in any env file has zero effect, by design. Only tuning env (thresholds, GPU flags, tokenizer behavior) applies. |
| **Harness** | `HARNESS_JUDGE_PROVIDER`/`HARNESS_JUDGE_MODEL` are the **one legitimate env-tier provider default** in the whole platform | This is LLM-as-**eval infrastructure** (the harness's own judge model for scoring runs during the offline PDSQI-9 gate), not tenant-facing generation — explicitly exempt from the "no provider default in env" invariant (see `apps/harness/.env.prod`'s own comment above these two keys). Runtime groundedness/reasoning sensors reuse the *same* `HARNESS_JUDGE_*` block, not a separate prefix. |

**Rule of thumb:** if a key's name ends in `_ENABLED`, `_BASE_URL`, `_API_KEY`, or `_ENDPOINT`, it's connection identity — safe to think of as "is this engine reachable/configured." If it ends in `_PROVIDER`, `_DEFAULT_MODEL`, or is a routing/chain variable, check the table above before assuming setting it changes what a tenant actually gets — for 4 of the 6 services, it either does nothing (NLP), is dev-only (guardrail), is informational-only (SMR), or doesn't exist (TTS).

## 4. Dev vs. test — what actually differs

`scripts/generate-env-file.sh`'s `_apply_test_overrides` is the authoritative list (read it directly for the current values). Summary by category:

| Category | Dev | Test |
|---|---|---|
| App ports | base (api 8868, stt 8861, smr 8862, guardrail 8863, nlp 8864, tts 8865, harness 8866, admin 5176) | **DEV + 100** (TASK-557) — api 8968, stt 8961, ..., admin 5276. Both stacks can run simultaneously without colliding. |
| Postgres | `:5432`, dynamic Vault-issued creds (`PG_DYNAMIC_CREDS=true`) | `:5433`, static `test:test` creds, `PG_DYNAMIC_CREDS=false` |
| Redis | `:6379`, no auth | `:6380`, `test_redis_pass` |
| MinIO/S3 | `:9000`, `minio_admin` | `:9002`, `test`/`testpassword` |
| Secrets provider | `vault` (real local Vault, dynamic) | `vault` (real local Vault, static AppRole — see below) |
| `JWT_SECRET_KEY` / `SESSION_SECRET_KEY` / `API_KEY_PEPPER` | Vault-resolved | fixed fake test-only strings, explicitly never for production use |
| `RATE_LIMIT_ENABLED` | `true` (module-bootstrap default) | `false` — Playwright runs fully parallel from one IP; the per-IP throttler would trip 429s across every spec's login (TASK-315). Enforcement is still covered by an in-process integration test with throttling pinned on. |
| `LOG_LEVEL` | `info` | `error` (quieter test output) |
| OTel | opt-in, off by default | forced off |
| Vault AppRole (`VAULT_ROLE_ID`/`VAULT_SECRET_ID`) | Minted by `scripts/refresh-vault-creds.sh` (called by `pnpm setup:dev`) | Minted by `scripts/test-setup.sh`'s own Step 2 (needs the shared `hope-vault` dev container up — the test infra does not run its own Vault) |

## 5. Per-service variable reference

Full per-key detail (name, default, purpose, mandatory-vs-tuning) lives as inline comments in `.env.sample` — that file **is** the enumerable reference, kept close to the values so it can't drift silently out of sync the way a separate hand-copied table would. This section is the *navigational* layer: what's mandatory to boot, what's a secret, and where to look.

| Service | Mandatory to boot (no code default) | Secrets (never commit real values) | Full reference |
|---|---|---|---|
| Root / API Gateway | `DATABASE_URL`; `JWT_SECRET_KEY`, `API_KEY_PEPPER`, `VAULT_SECRET_ID`/`VAULT_WRAPPED_SECRET_ID` when `SECRETS_PROVIDER=vault` | `JWT_SECRET_KEY`, `SESSION_SECRET_KEY`, `API_KEY_PEPPER`, `*_SERVICE_TOKEN` (×6), `MINIO_*`, `S3_*`, `REDIS_PASS`, `AZURE_*_KEY`, `OIDC_CLIENT_SECRET` | `.env.sample` §1–2; `docs/implementation/TASK-558-Environment-Configuration-Refactor/env-surface.generated.md` (generated, authoritative for tier/required/default per key) |
| Guardrail | None — every field has a code default | `GUARDRAIL_SERVICE_TOKEN`, `GUARDRAIL_OPENAI_COMPAT_API_KEY` (+ optional Azure/Bedrock/vLLM keys) | `.env.sample` §5; `apps/guardrail/.env.sample` |
| Harness | Conditionally: `HARNESS_CLAIM_CHECK_STORE=s3` (+ S3 creds) is *effectively* mandatory outside dev (the process refuses to boot with `store=memory` in a `production`/`staging` `HARNESS_ENVIRONMENT`) | `HARNESS_SERVICE_TOKEN`, `HARNESS_INTERNAL_SERVICE_TOKEN`, `HARNESS_CLAIM_CHECK_{ACCESS,SECRET}_KEY`, `HARNESS_JUDGE_OPENAI_COMPAT_API_KEY` | `.env.sample` §6; `apps/harness/.env.sample` |
| NLP | None | `NLP_SERVICE_TOKEN` | `.env.sample` §7; `apps/nlp/.env.sample` |
| SMR | None | `TEXT_SERVICE_TOKEN`, `TEXT_{OPENAI,ANTHROPIC,AZURE}_API_KEY` | `.env.sample` §8; `apps/text/.env.sample` |
| STT | None (pydantic-required); functionally mandatory: `DATABASE_URL`, `MINIO_*`, `REDIS_URL`, `API_GATEWAY_KEY` (both FastAPI app and Dramatiq worker connect eagerly at startup) | `API_GATEWAY_KEY`, `AZURE_SPEECH_KEY`, `AZURE_FOUNDRY_API_KEY`, `SARVAM_API_KEY`, `OPENAI_API_KEY`, `AZURE_STORAGE_*` | `.env.sample` §9; `apps/stt/.env.sample` |
| TTS | None | `TTS_SERVICE_TOKEN`, `TTS_SARVAM_API_KEY`, `TTS_AZURE_API_KEY` (or shared `AZURE_SPEECH_KEY`) | `.env.sample` §10; `apps/tts/.env.sample` |

## 6. Known gaps (documented so they aren't rediscovered)

- **Resolved (TASK-585):** `.env.sample` was hand-assembled and not CI-gated at TASK-583/584 time. `pnpm env:sync` now generates it directly (§2), so `env-drift-check` covers the whole file, not just the 4 TypeScript-generated sections.
- **The Python `.env.sample` files' own CONTENT stays outside `pnpm env:sync --check`** for the same reason TASK-558 originally accepted: the CI job that runs the drift check has no Python environment to import pydantic-settings from. This is a pre-existing, deliberate boundary, not new to TASK-583/584/585 — but the generator does still read those 6 files from disk and fail `--check` if the ASSEMBLED `.env.sample` drifts from them, so an edit to a Python file that isn't followed by `pnpm env:sync` is still caught.
- **`scripts/test-setup.sh`'s Vault-provisioning step (Step 2) is unchanged by TASK-583** — it still mints real local AppRole credentials and mutates `.env.test` in place. That's fine now because the target file is gitignored, but it means `.env.test` still ends up holding real (if merely local-dev-scoped) secret material — never hand-copy its contents into a tracked file.
- **The per-service `.env.prod` files are out of scope here** — they're deployment reference templates (§1 table), not local-setup artifacts. See `.claude/rules/09-infrastructure-devops.md` §Configuration Tiers for the DB/Vault-tier vs. env-tier framework governing what belongs in a real deployment.
