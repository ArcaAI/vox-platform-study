## Data model map

```

 ├─ ContextItems: ContextItem[]                     (1-to-many; the aggregate)
 ├─ Highlights: Highlight[]                         (doctor manual marks, NOT part of NER/context taxonomy)

ContextItem  (the reference's "consultation context item")
 ├─ type: ContextItemType   (AUDIO_RECORDING|WORKNOTE|RAW_SUMMARY|MODIFIED_SUMMARY|PRE_SUMMARY|NAMED_ENTITY|TRANSCRIPT|CASE_NOTE|ATTACHMENT|SIGNED_NOTE|STRUCTURED)

 ├─ kindKey / contextSchemaVersionId   (tenant-declared kind + the PINNED schema version it was validated against — write-time capture)
 ├─ encryptedContent (Vault-Transit; no plaintext column)
 ├─ mediaId / dnaWritingStyleId        (soft references, no FK)
 ├─ currentVersionNumber
 ├─ resourceStatus (ENABLED|DISABLED|SUSPENDED|ARCHIVED|DELETED — standard soft delete)
 ├─ qdrantSynced / qdrantSyncedAt      (dead flag — target collection never provisioned; consultation.prisma:123-133)
 ├─ AudioRecordings[] / SummaryMeta (1:1) / NamedEntities[] / Versions: ContextItemVersion[] / TranscriptSegments[]

 ├─ versionNumber, changeReason, changedBy, changeSource

 └─ attestedAt / attestedBy / attestationHash / modelName / modelVersion / sensorScores   (populated ONLY on the SIGNED_NOTE version written by approveSummary)

SummaryMeta (1:1 with a RAW_SUMMARY/MODIFIED_SUMMARY/PRE_SUMMARY ContextItem)
 ├─ two-phase assurance: gateDecision / assuranceCompletedAt (null = DRAFT_PENDING_SENSORS)
 ├─ encryptedCitationsMap (claims: [{id, text, section S|O|A|P, confidence, status verified|unverified, evidence:[{transcriptContextItemId,startOffset,endOffset,quote}], entityRefs, knowledgeChunkIds}])

NamedEntity  — className, umlsCui/snomedCode/rxnormCode/icdCode/loincCode (columns exist, READ by summarization, WRITTEN BY NO CODE — consultation.prisma:391-406 comment), transcriptContextItemId + offsets (span provenance), assertion (PRESENT|ABSENT|HISTORICAL|FAMILY|HYPOTHETICAL)

TranscriptSegment — per-(contextItem,idx) ordinal, t0Ms/t1Ms, speaker, charStart/charEnd into the parent's decrypted content. NO "partial" flag; NO persisted representation of a still-streaming partial.

Highlight — doctor-authored manual mark (W3C selectors), soft-reference `sourceContextItemId` + `targetKind`. Orthogonal to NamedEntity so manual marks never pollute AI NER.

ConsultationContextSchema / ConsultationContextSchemaVersion (consultation-context-schema.prisma)
 ├─ head row (mutable, DRAFT|PUBLISHED|APPROVED) + immutable per-publish Version snapshot + movable `pinnedVersionNumber` pin
 ├─ 5 CLOSED platform primitives a tenant-declared "kind" must map to: STREAM_AUDIO | TEXT | DOCUMENT | IMAGE | STRUCTURED
 └─ REAL and load-bearing: `ContextService.addContext/updateContext` calls `resolveContextKind` → `ConsultationContextSchemaService.validateContextPayload`, which resolves the version the CALLER pinned to (never silently upgraded) and validates a STRUCTURED payload against its JSON-Schema-subset `fields`. NOT scaffolding — full CRUD + governance (breaking-change detection, checksum-idempotent republish, per-(tenant,scope,department) default) verified by direct full read of consultation-context-schema.service.ts (524 lines).

AgentTrajectoryStep (agent-trajectory.prisma) — ordered per-session step stream (LLM_CALL/TOOL_CALL/SENSOR/RETRIEVAL/GUARDRAIL/THINKING/SIGNAL/GATE/PHASE), correlated to OTel trace, `payloadRef` claim-check only (never plaintext). TENANT-scoped, NO soft-delete, NO sys-event (own event stream). Nightly hard-delete prune exists (`AgentTrajectoryRetentionService`, OFF by default). This is where MCP `TOOL_CALL`s actually land (`apps/harness/src/harness/temporal/activities.py:801-860`) — NOT in `AuditLog` or `HarnessAuditEvent`.

HarnessAuditEvent (harness.prisma) — the WORM ledger. Identity-only row (no `_version`/`resourceStatus`/`updatedAt`). The `REVOKE UPDATE, DELETE` claim in the schema comment is CONFIRMED present in migration SQL (`packages/database/src/prisma/db_main/migrations/20260606143138_task_330_add_clinical_harness_eval_and_worm_audit/migration.sql` — Agent B). `action: HarnessAuditAction` (GENERATE|SENSOR_RUN|GATE_DECISION|ATTEST|CONSENT_GIVEN|CONSENT_WITHDRAWN|BREACH_REPORTED|REDUCED_ASSURANCE|SAFETY_OVERRIDE|SIGNED_BEFORE_ASSURANCE|POST_SIGN_FLAG|GATE_ESCALATED|GATE_ABANDONED). 9 of these 12 actions are genuinely wired end-to-end (GENERATE/SENSOR_RUN/GATE_DECISION/ATTEST/REDUCED_ASSURANCE/SAFETY_OVERRIDE/SIGNED_BEFORE_ASSURANCE/POST_SIGN_FLAG/GATE_ESCALATED/GATE_ABANDONED — confirmed by Agent B). `CONSENT_GIVEN`/`CONSENT_WITHDRAWN` and `BREACH_REPORTED` have **zero writers anywhere in TS/Python source** — dead enum values (consistent with no `Consent` model existing at all).

AuditLog (audit.prisma) — the GENERAL sys-event-driven audit trail (CREATE/READ/UPDATE/DELETE/ARCHIVE/LOGIN/LOGOUT/IMPERSONATED_ACTION), envelope-encrypted (`encryptedData`/`encryptedPreviousData`, cached-DEK AES-256-GCM), `ResourceType` enum (62 values, confirmed 1:1 parity with the domains-layer TS enum by both me and Agent B independently). NOT DB-privilege WORM (ordinary table; retention purge below HARD-deletes it, which a true WORM table would forbid). **Critically: a `ResourceViewed` sys-event broadcast does NOT by itself produce an `AuditLog` row** — see Finding F-11.

DnaWritingStyleReport / DnaWritingStyleVersion (dna-writing-style.prisma) — encrypted report/style-text/redaction-rules, `isLatest` + `currentVersionNumber`. See Finding F-13 (VIOLATED) for the write path. `DnaUsageRecord`/`PromptUsageRecord` — plain-id usage logs, no FK.

GateEditExemplar (harness.prisma) — derived, PHI-redacted-**at-write** learning corpus mined from the approve-vs-edit signal (RAW_SUMMARY→MODIFIED_SUMMARY diff). Explicitly documented as "a DERIVED projection, never the audit truth," with redaction happening BEFORE persistence (harness.prisma:433-436). This is the standard the DNA-writing-style path is held to and fails to meet (F-13).

KnowledgeDocument / KnowledgeChunk (knowledge.prisma) — tenant RAG corpus feeding the harness JIT retriever; DRAFT→APPROVED→ARCHIVED; Qdrant point-id provenance per chunk.

There is **no `Consent` model, no ABAC model, and no per-artifact-class retention-TTL model anywhere in the schema.** Confirmed by full-schema read + repo-wide grep (zero hits for `consent`/`ABAC` outside unrelated OAuth-scope comments and free-text template field names).
```

### F-01 detail — Consent + ABAC grant: ABSENT

**Reference requires:** T1 — "Compliance agent evaluates patient consent (grant, view, revoke, time-limit) and clinician ABAC... Every subsequent retrieval is audited against this grant." US-CO-03 — "the tool gateway to deny any call that does not match the patient's active consent scope, with a logged denial." US-PT-01 — patient can grant/view/revoke/time-limit consent.

**Code today:** No `Consent`, `ConsentGrant`, `ABAC`, or equivalent model exists in any of the 41 `.prisma` files under `packages/database/src/prisma/db_main/`. Repo-wide grep for `consent`/`ABAC` across `packages/domains`, `packages/applications`, `apps/api`, `apps/harness`, `apps/text`, `apps/guardrail` returns zero relevant hits — the only matches are an MS-Graph OAuth-admin-consent comment (`ms-graph-directory.provider.ts:27`) and a free-text template field literally named `patient_education_and_consent` (`dept-templates.ts:151/164`, a markdown field label for a note template, not a data model). `HarnessAuditAction` carries `CONSENT_GIVEN`/`CONSENT_WITHDRAWN` enum values (harness.prisma:24-25) — Agent B confirmed **zero writers anywhere in TS/Python source**, only the enum declaration.

**Failure scenario:** There is nothing in the platform that gates a retrieval, a terminology-MCP call, or a drug-interaction lookup on a "patient has an active AI-drafting consent" check. Authorization today is entirely tenant/role-based (RBAC via `@Authorize`/`@CanRead` etc., `apps/api`'s `UnifiedAuthGuard`), which answers "is this caller allowed to touch this tenant's data" — never "has THIS patient consented to AI documentation of THIS encounter." A patient who has never consented (or has actively revoked) has no mechanism to block a session from starting or a tool call from firing.

**Blast radius:** Every downstream requirement that assumes a consent record exists is unimplementable as specified: US-CO-03 (consent-gated tool calls), US-PT-01 (patient consent self-service), UC-18 (revocation cascade — F-09), T1's compliance gate before priming, and F-13's own "scrub on revocation" requirement (there is nothing to scrub FROM, since there is no consent to revoke).

### F-03 detail — Contradiction detection: ABSENT

**Reference requires:** T6.1 — "NLP/Reasoning Agent emits a `contradiction.detected` event. Master/Harness loop does not resolve the conflict... Silently preferring speech or image is forbidden." T12.4 — same pattern for historical-allergy-vs-current-transcript. UC-09/UC-10 — a typed contradiction item with both sources + timestamps + a `contradicts` link; finalization blocked for safety-critical slots until clinician resolution.

**Code today:** No `ContextItemType` value, no context-item "kind," no domain event, and no service method anywhere implements contradiction detection between (a) transcript vs. image findings, or (b) transcript vs. imported history. The `groundedness`/`entailment_batch`/`citation_verify` inferential sensors check whether a CLAIM is supported by the transcript (a one-sided grounding check), a different concept from detecting that TWO sources disagree with each other.

**Failure scenario:** A patient states "no prior surgery" in the transcript while an attached CT report shows post-operative clips (the reference's own T6.1 example). Today's pipeline: the CT is OCR'd/described (ATTACHMENT), the speech is transcribed (TRANSCRIPT), both feed NER/summarization independently, and the composed note simply reflects whatever the generation model does with both inputs in its prompt — there is no code path that detects the disagreement, creates a durable "contradiction" record, or blocks finalization pending clinician disambiguation.

**Blast radius:** One of the 12 "core consensus" items in the source-paper synthesis (§5 of user-stories-and-use-cases.md). Its absence means a documented, multiply-cited requirement for the core safety story has no code representation at all.

### F-06 detail — Section-level HITL: ABSENT (whole-document granularity only)

**Reference requires:** US-CL-13 — "approve, edit, or reject each section of the final summary independently, with an audit trail on every decision... FINALIZED is unreachable until all required sections are approved." T20 — "Harness records per-section approve, edit, reject, or return-for-regen as separate audit events."

**Code today:** `SummaryService.approveSummary` (`summary.service.ts:824-1027`) operates on exactly one `ContextItemId`, guarded by `contextItem.isFinalSummary` (RAW_SUMMARY or MODIFIED_SUMMARY — a whole document). It writes ONE `SIGNED_NOTE` `ContextItemVersion`, appends ONE `ATTEST` WORM event, and flips `Consultation.status` to `SIGNED`. Agent A confirms independently: `LiveSummarySectionDto` (`live-summary.dto.ts:72-78, 261-262`, `{title, content}`) is produced by parsing the flat `runningSummary` string at DISPLAY time (`parseSoapSections`/`parseSoapJson`) — it carries no id, no version, no independently-tracked state, and `HarnessGateDecisionRequest`/`recordGateDecision()` records ONE aggregate `PASS|REGEN|FLAG` verdict for the whole generated note. **Failure scenario:** A clinician approves the Assessment and Plan sections of a note but wants the (AI-hallucinated) Subjective section regenerated. Today's only mechanism is: edit the WHOLE note's content directly, or sign the whole thing as-is. There is no way to record "Assessment: approved; Subjective: rejected, regeneration requested" as two separate, independently-audited decisions.

**Blast radius:** Every section-level requirement collapses to whole-document behavior: US-SC-03 (draft/verified/approved labels per section), QA's ability to see "which sections were AI-accepted versus rewritten" (US-CL-13's own acceptance criterion), and the harness's own bounded regen loop operates on the WHOLE generated note text.

### F-07 detail — Retention TTL by artifact class: PARTIAL

**Reference requires:** US-AD-04 — "set retention TTLs per artifact class per jurisdiction so that session scratch, drafts, and finalized notes expire correctly... Raw scratch and unapproved drafts expire independently of the finalized EHR note." T23 — "Harness archives the session, expires short-term context items per tenant TTL."

**Code today:** Two real, well-built, self-scheduling cron services exist: `AuditRetentionService` (purges `AuditLog` rows older than one configurable `retentionDays`, batched hard-delete, default OFF) and `AgentTrajectoryRetentionService` (mirrors it for `AgentTrajectoryStep`, default OFF, 30-day default window). Both read config live from `AppSettingsService` (DB-backed `GlobalSetting`, ~45s refresh) — genuinely operable without a redeploy. **However:** each job is ONE flat window for ONE entire table — no per-class TTL WITHIN a table, and neither job (nor anything else found) ever touches `ContextItem`/`ContextItemVersion` — the actual session-scratch/draft/transcript rows the reference means. A `ContextItem` only leaves the ENABLED set via an explicit user-initiated `deleteContext` soft-delete; nothing auto-expires it by class or by session-close event.

**Failure scenario:** A consultation is abandoned unsigned (the UC-12 `PENDING_REVIEW`-forever/abandoned-gate path — see F-10). Its raw transcript, work-note drafts, NER rows, and unsigned RAW_SUMMARY all remain live (`resourceStatus = ENABLED`) indefinitely — no TTL job will ever expire them, regardless of tenant policy, because no such policy surface exists for `ContextItem`.

**Blast radius:** Directly undercuts T23's "short-term working artifacts expire after close" and US-AD-04's per-class configurability premise — the two TTL jobs that DO exist cover only operational telemetry (audit log, agent trajectory), not clinical scratch data.

### F-11 detail — PHI reads: ABSENT from the durable ledger by default (corrects an earlier working assumption)

**Reference requires:** US-CO-01 — "every PHI access, model call, tool call, and HITL decision recorded on an immutable, tamper-evident ledger."

**Code today:** Every read-path method in `context.service.ts`/`consultation.service.ts` DOES broadcast `SysEventType.ResourceViewed` (`getContextItems`, `getContextItemWithRelations`, `getVersionHistory`, `diffVersions`, `getSharedContext`, `getAggregateNamedEntities`, `getContextItemsPaginated`, `getById`, `getByIdWithRelations`, `getPatientHistory`, etc. — confirmed by my own line-by-line read of both files). This LOOKS like read-auditing coverage. Agent B traced the consumer, `SysEventService.handleResourceViewedEvent` (`sysEvent.service.ts:239-254`), and found it only writes an `AuditLog` row **`if (!event.disableAuditLog && event.forceAuditLog)`**; otherwise the event only enqueues an ephemeral BullMQ job (`removeOnComplete: true`) for webhook fan-out. `forceAuditLog: true` is set ONLY on `GlobalSetting`/RBAC `Policy`/`Role` reads — **never on any clinical `Consultation`/`ContextItem` read.** So: a plain GET of a patient's transcript, summary, or NER results is broadcast as a `ResourceViewed` event but is **not durably recorded** in `AuditLog`.

**Tool calls:** `call_mcp_tool` (`activities.py:801-860`) DOES emit a `TOOL_CALL` `AgentTrajectoryStep` — but that table is explicitly documented as high-volume ops telemetry with hard nightly-prune retention (F-07's sibling), not a durable audit ledger, and carries no sys-event/AuditLog mirror.

**HITL decisions:** genuinely well covered — `GATE_DECISION`/`ATTEST`/`SAFETY_OVERRIDE`/`SIGNED_BEFORE_ASSURANCE` are all written to the WORM `HarnessAuditEvent` with `clinicianId`/`attestationHash` (Agent B).

**Failure scenario:** A support engineer or a compromised session lists every `ContextItem` in a consultation via `getContextItems`/`getContextItemWithRelations` (a PHI read of transcript, work notes, and summaries). The event fires, a webhook job is queued and completed, and then discarded (`removeOnComplete: true`) — no row survives in `AuditLog`. A HIPAA §164.312(b) access-log review of "who read this patient's chart and when" cannot be answered from the durable ledger for this access.

**Blast radius:** US-CO-01's "every PHI access... recorded" is the strongest shared safety rule across all four source papers alongside "timeout is not approval." This is the one half of it (access, as opposed to mutation/tool-call/HITL) the code does not durably satisfy.

### F-13 detail — DNA writing-style: VIOLATED (from Agent B, verified evidence chain)

**Reference requires:** US-CL-11/T11/T22 — "the profile holds structure, abbreviations, verbosity, hedging, list-versus-narrative — never patient clinical facts... Learning is from approved notes... Patient facts never enter the style profile." UC-04 — "Style profile contains no patient clinical data." T22 — "A later consent revocation scrubs that patient's contributions from the exemplar bank per policy."

**Code today (full trace, trigger → source → ciphertext):**
1. `POST /dna-writing-styles/generate` (`apps/api/src/modules/dna-writing-style/dna-writing-style.controller.ts:90-100`) and `POST /admin/dna-writing-styles/generate/:doctorId` (`dna-writing-style-admin.controller.ts:158-168`, gated only by `@Authorize(['manage','DnaWritingStyleReport'])`, no doctor-ownership check) both accept an optional `textSamples: string[]` (`generate-dna-report.request.ts:4-9`) validated only as `@IsArray()/@IsString({each:true})` — no length cap, no PHI scan, no provenance constraint.
2. `DnaWritingStyleProcessor.processWithContext` (`dna-writing-style.processor.ts:105-111`): `if (textSamples?.length) { samples = textSamples.join(...) } else { /* only HERE does the approved-only-notes filter apply */ }`. Supplying `textSamples` **completely bypasses** the approved-notes gate.
3. The samples are posted to SMR with the `DNA_ANALYSIS` prompt template (seed content: `packages/database/src/prisma/db_main/seed/07-prompt-template.ts:389-390`), which instructs only "Analyze the physician's writing style... Output a structured DNA profile" — no instruction to exclude patient facts/medications/identifiers.
4. The LLM's raw output is parsed and persisted with **zero redaction transform**, via `DnaWritingStyleReportRepository.encryptFieldsIntoEntity` — a pure encrypt-passthrough.
5. `DnaWritingStyleService.getEffectiveStyleText` decrypts this and is injected into `smr-compat.controller.ts:284-302`'s prompt for an UNRELATED patient's summary generation.

**Standard comparison:** `GateEditExemplar` (harness.prisma:433-436) explicitly documents "PHI-redacted before/after snippets. Redaction happens BEFORE persistence" for a sibling learning-corpus store in the SAME codebase. The DNA path has no equivalent step anywhere — even the gated/automatic branch (no `textSamples`) only filters WHICH summaries are eligible, never redacts their CONTENT before sending to the LLM or persisting the output.

**Concrete failure scenario:** A doctor (or any tenant admin, for any doctor) calls the generate endpoint with `textSamples: ["Patient John Doe, MRN 12345, on Warfarin 5mg..."]`. This skips the approval filter, is sent to SMR verbatim, and the model's echoed response is encrypted and stored as that doctor's permanent "writing DNA." The next time that doctor sees an unrelated patient, `getEffectiveStyleText` decrypts and injects this text into the NEW patient's summary prompt — a direct cross-patient PHI leak with no consent check anywhere in the chain.

**Blast radius:** Directly violates the reference's own explicit VIOLATED-hunt target (T11/T22/UC-04's "never patient facts," "PHI-free exemplar bank") and, combined with F-01/F-09 (no consent, no revocation cascade), means there is no mechanism at any layer to prevent or later remediate this leak.

### F-14 detail — Protected user-authored text: VIOLATED for two AI write paths (from Agent A, verified evidence chain)

**Reference requires:** T5/T12/T12.2 — "User-authored text is protected from automatic overwrite... The system must not silently restore the old wording." US-CL-06 — "patches require a visible diff." US-CL-10/UC-08 — clinician correction is authoritative, "the system never silently restores the old wording."

**What genuinely works** (see F-12): inside a single `HarnessDocWorkflow` execution, `self._edited`/`self._ever_edited` sticky state disables the "regen-if-untouched" auto-swap once any clinician edit lands during the post-generation assurance window — a real, well-engineered guard (its own code comment: "Once edited, a REGEN-fixable issue must SURFACE as a FLAG (never swap the clinician's note)").

**Where it breaks — Path 1, harness draft re-adoption (`harness-internal.service.ts`):** `findOwnHarnessDraft()` (lines 1302-1321) locates a prior draft **purely by an ownership marker** (`metaData.subType === HARNESS_DRAFT_SUBTYPE`) — never by checking whether the row has since been clinician-edited. `persistDraft()`'s adoption branch (lines 761-774) then does:
```ts
if (existingDraft) {
  existingDraft.content = strippedContent;   // unconditional overwrite
  ...
  await this.contextItemRepository.update(existingDraft.id, existingDraft);
```
The code's own comment (lines 745-758) documents this as a ROUTINE scenario: `HarnessDocWorkflow` has two start sites (`ConsultationEventHandler`'s Lane-G auto-summary, and `ConsultationLoopWorkflow`'s `harness.finalize` child), both targeting the deterministic workflow id `harness-doc-{consultationId}` — Temporal's `ALLOW_DUPLICATE` only rejects a second start while the first execution is OPEN, so a second execution — with brand-new, non-carried `_edited=False`/`_ever_edited=False` state — is routine, not an edge case.

**Concrete failure scenario (Path 1):** First `HarnessDocWorkflow` execution delivers a draft (RAW_SUMMARY, `metaData.subType = HARNESS_DRAFT`), reaches `PENDING_REVIEW`, closes. Clinician edits it via `PATCH` → `SummaryService.updateSummary()`, which writes a v2 `ContextItemVersion` with `changeSource: 'doctor_edit'` — but `type` stays `RAW_SUMMARY` and `metaData.subType` stays `HARNESS_DRAFT`, so nothing distinguishes it from an unedited draft to the adoption check. The consultation later ends; `ConsultationLoopWorkflow._start_finalize_child` starts a FRESH `HarnessDocWorkflow` (same deterministic id, now permitted since the first closed) with fresh edit-tracking state. It runs the full generation pipeline and calls `persist_draft` → `HarnessInternalService.persistDraft` → `findOwnHarnessDraft` finds the (now clinician-edited) row → `existingDraft.content = strippedContent` silently replaces the clinician's correction with fresh AI wording. `persistDraft` additionally resets `consultation.status` to `PENDING_REVIEW`/`DRAFT_PENDING_SENSORS` unconditionally (line ~892-896), regardless of whether it had already progressed further.

**Where it breaks — Path 2, live-documentation durable snapshot (`live-documentation.service.ts:1802-1873`):** `persistDurableSnapshot()`, called every `LIVE_DOC_DURABLE_SNAPSHOT_MS` (default 30s), upserts the `LIVE_SOAP_SNAPSHOT` PRE_SUMMARY `ContextItem`:
```ts
} else {
  session.snapshotEntity.content = content;   // in-memory AI content, unconditionally
  ...
  await this.contextItemRepository.update(session.snapshotEntity.id, session.snapshotEntity);
}
```
There is **no read-back of the DB row and no version/edit check at all** — `content` always comes from the in-memory `session.lastPayload.runningSummary`. This PRE_SUMMARY row qualifies as `isSummary` (`context-item.response.ts:259`), so `SummaryService.updateSummary()` accepts direct clinician edits to it, guarded only by the post-signature `"Summary is approved and locked"` check (`summary.service.ts:713-716`) — which does not apply here since a PRE_SUMMARY is never approved. **The only "locked" concept found anywhere in the codebase is this one, and it protects the opposite direction** (blocking further CLINICIAN edits after sign-off) — it gates no AI-side write path at all. No `locked`/`protected`/`userEdited`/`clinicianEdited`/`isDirty`/`manualEdit`/`frozen` field exists on `ContextItem` (confirmed against the full schema) or anywhere in `packages/applications/src`.

**Concrete failure scenario (Path 2, the MORE directly reachable of the two — every live session hits this loop):** Clinician directly edits the live running SOAP note mid-consultation to correct a medication dose. Within 30 seconds, `persistDurableSnapshot`'s next periodic flush overwrites `content` with the loop's own next AI-generated summary, with zero awareness the row was just hand-edited — exactly the "silently restore old wording" failure mode T12.2 forbids by name, on the highest-frequency write path in the whole session.

**Blast radius:** This is a direct, repeated violation of one of the reference's most-repeated invariants (named in US-CL-06, US-CL-10, T5, T8, T12, T12.2, T16, T20 — arguably the single most load-bearing safety rule after "timeout is not approval" and "the system never signs"). Path 2 in particular fires on ordinary, expected usage (every live session with periodic snapshotting), not an edge case.

## Divergences

- The reference's context-item lifecycle is a per-ITEM 7-state machine; the code's only typed lifecycle is per-CONSULTATION (`ConsultationStatus`). This is a structural divergence, not a bug — the code was clearly built around "consultation as the unit of lifecycle," and the reference (a later, more granular redesign target) wants item-level and eventually section-level granularity. Treat as the single biggest architecture gap between reference and code — F-02, F-06, and half of F-14's blast radius all trace back to this one modeling choice.
- `resourceStatus` (ENABLED/DISABLED/SUSPENDED/ARCHIVED/DELETED, the house soft-delete convention) is being asked to do work the reference's Flagged/Invalidated/Superseded states would otherwise cover, and it cannot: soft-delete is a binary visibility switch, not a semantic state.
- The reference's "Session checkpoint" concept assumes an explicit, addressable checkpoint artifact; the code gets resumability "for free" from Temporal's durable-execution model, which is architecturally sound but means there is no queryable "here is the checkpoint at T13" object — durability and explicit modeling are conflated in the reference but are genuinely different things in the code.
- The reference treats "audited" as roughly binary (an access either is or isn't recorded). The code's actual posture is a three-tier system — WORM `HarnessAuditEvent` (immutable, DB-privilege-enforced) / ordinary `AuditLog` (encrypted, sys-event-driven, hard-deletable by retention) / ephemeral BullMQ sys-event job (never persisted unless `forceAuditLog: true`) — and PHI reads land in the weakest tier by default (F-11). The reference should be explicit about which tier it means by "recorded on an immutable, tamper-evident ledger," since the code has three answers to that, only one of which is actually immutable.

## [ADDED] invariants

- **[ADDED-1]** A `ContextItem` write should record, at minimum, which upstream item (if any) it was derived from, so a future invalidation cascade has something to walk. Partial infrastructure for this already exists and is under-used: `context.service.ts`'s `resolveCascadeDepth`/`derivedFromContextItemId`/`metaData.loopDepth` (lines 255-275, 348-351) tracks CASCADE DEPTH for the loop's dispatch bookkeeping, but does not persist a durable, queryable `derivedFromContextItemId` column on the row — it round-trips through `metaData` best-effort only. This is the load-bearing precondition for F-06/T12.2's invalidation-cascade requirement and is currently the closest the codebase comes to it.
- **[ADDED-2]** Given F-07, a `ContextItem`-level `expiresAt` (or a class-lookup table keyed by `type`) is the natural, additive schema change that would let a real US-AD-04 be built without redesigning the two existing retention-service patterns — they already prove the cron/AppSettings-live-config pattern works.
- **[ADDED-3]** Given F-14, any write path that mutates `ContextItem.content` on behalf of an AI process should be required to read the row's `currentVersionNumber` (or a new `lastEditSource` field) immediately before writing and refuse/divert-to-flag on a mismatch — exactly the pattern F-12 already implements successfully within one workflow execution, generalized to a durable column instead of in-process state so it survives across the re-entrant write paths identified in F-14.
- **[ADDED-4]** Given F-11, any sys-event broadcast on a read of PHI-bearing resource types (`Consultation`, `ContextItem`, `ContextItemVersion`, `SummaryMeta`, `NamedEntity`, `AudioRecording`) should default `forceAuditLog: true` rather than requiring each call site to opt in — the current opt-in-per-call-site design is exactly the kind of "silently missing" gap this reference's US-CO-01 exists to catch.

## Reference defects

- The dataset.xml's own Note at T21 says "QA can later open the provenance graph: transcript spans, retrieved snippets, tool calls, evaluator scores, and HITL edit history" as though this is a single graph object. In the actual code, this data is real and joinable but lives in at least four separate tables (`SummaryMeta.encryptedCitationsMap` for transcript-span+chunk evidence, `AgentTrajectoryStep` for tool calls/LLM calls, `HarnessAuditEvent` for gate/attest events, `ContextItemVersion` for HITL edit history), joined only by shared `consultationId`/`contextItemId` foreign keys, not a purpose-built graph structure. The reference should be explicit that "provenance graph" means "joinable via shared ids across N tables," since a QA reviewer today would need to know all four tables exist and how to join them — there is no single read API confirmed to assemble this in one call (open question #3 below).
- UC-06's "escalate to HITL merge" and the general safety principle "silently preferring [X] over [Y] is forbidden" are in tension with a design that ALSO wants an autonomous multi-specialist loop to make forward progress without blocking on a human for every disagreement (the workflow is explicitly `PURE`/deterministic and replay-safe, i.e. designed to run without external interruption). The reference does not resolve this tension — it never explains what "HITL merge" means operationally for a Temporal workflow that cannot pause indefinitely for a human mid-run the way the single-clinician session can. The code arguably had to answer this on its own (auto-resolve-and-record, F-08), and the reference should be explicit about whether "escalate" means "block the multi-specialist run" or "surface post-hoc for clinician review at the final note."
